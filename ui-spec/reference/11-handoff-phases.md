# 11 · 实施交接与依赖顺序 v3.0

完整UI设计已按本轮范围推进，后续工程以[15 UI契约矩阵](15-ui-contract-matrix.md)处理已有能力的保留与新增设计的接入。阅读顺序：00→HANDOFF→12→15→对应页面/组件→10/16。真实项目目录、状态层、IPC与测试脚本在接入前读取当前仓库，不凭附件猜建目录或依赖。

## 1. 交付依赖

| 阶段 | 独立交付范围 | 前置条件与出口 |
|---|---|---|
| 共享基础 | Starlight Gold语义Token、45组件、键盘/浮层/表单契约 | 实际旧样式与变量映射；02/10组件与布局用例 |
| 外壳与首次使用 | 五区、导航、窗口/缩放、欢迎/认证/引导 | 共享基础；三平台替代路径同时接入 |
| 工具与账号 | 来源/共享配置/启动安装；九页签/Key/报价订单 | 对应已有能力适配；新增多账号单独保留隔离契约 |
| 扩展与内容 | 聊天/记录、MCP/技能/插件、备份、画布 | Provider/capability与保存/任务接口；不能遗漏只读和恢复 |
| 维护与系统 | 设置、检查/报告、教程、更新、托盘/深链/通知/迁移 | UI状态可先适配；原生能力按Windows/macOS/Linux分别验收 |
| 切换与发布准备 | 完整功能对照、数据保护、回归、发布候选 | 所有已选接入范围有真实证据，缺口明确，不借切换删除旧能力 |

Windows/macOS/Linux贯穿各阶段，Linux不再整块延后。各平台可以按真实能力提供外部安装或替代入口；不能因某项原生服务尚未接入就把整个平台UI删去。

每个PR交付一个能独立验收的范围，阶段可拆多个PR。先复用实际仓库适配器、选择器和状态约定，再决定新增目录或组件结构；`src/renderer-v2`、特定组件文档工具、渲染层开关都不是本规范指定的既成结构。

每条G01–G19记录：固定源码事实→最新仓库复核→新UI入口/字段/状态→保留或新增→能力条件/平台→接口或IPC适配→UI证据→真实运行证据。矩阵的UI模拟状态不应被改写成真实后端完成。

主应用组件基线正文14、控件36/32/28；密集例外见01。旧灰绿主题的实际变量先定位后映射到新语义Token，不按颜色近似全局替换。Logo和品牌源保留，不重绘，不把通用图标套到厂商资源。

PR描述写具体问题、结果行为、范围、实际验证命令、截图和未测项；不粘贴会话历史、模拟通过数字或未经核实的性能结论。现有测试选择器在可用时保留，测试名称以仓库实际脚本为准。

## 3. 数据迁移与回滚

固定证据基线是GitHub `0c9ec4a5a3c9cf31fa0e05c33725cd31ae73e39e` / `0.1.31`，不是迁移格式保证。升级区间、账号存储、配置/会话格式和路径从真实代码与样本确定。

迁移前保留源快照、格式版本与校验；写独立目标路径，验证通过后切读取路径。失败保留原文件。回滚前再保留新版时点快照，**不删除新版数据**；按字段说明能逆迁移和只能保留待恢复的内容。

凭据沿用经核实的安全存储，不把快照变成明文日志。迁移/回滚/导出/清除明确工具配置、账号、会话、索引、项目文件的各自范围，不用“所有数据”含混带过。

必须验证“迁移→新版新增/修改→回滚→旧模式可读与新版快照可定位→重新进入新版或恢复”。失败或取消后的当前读取路径、可用数据、剩余步骤可追踪；不能以旧文件仍在证明新版数据安全。
