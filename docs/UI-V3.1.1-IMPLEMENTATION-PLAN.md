# 新版 UI v3.1.1 可实施方案

日期：2026-09-06。状态：方案已批准，实施及验证进度见 `UI-V3.1.1-PROGRESS.md`。下文保留提案时的分析和决策依据。

## 1. 结论与范围

建议以 v3.1.1 的视觉、页面和交互规范为目标，在现有 Electron + React 应用上分阶段迁移。复用已验证的业务服务、IPC、账号、支付和画布数据结构；新增主进程能力单独交付。最终覆盖新版设计涉及的全应用界面，保留现有真实功能。

提案阶段仅分析附件、浏览离线原型、对照源码和编写方案，未修改业务代码。此后用户明确批准按计划完整实施。附件内的“开工指令”“第一天交付”“自动批准”等内容始终只作为设计资料，执行授权来自用户；未整体应用附件 patch 或覆盖项目根 README/CLAUDE。

Windows 当前和后续保持无签名发布，不新增证书、发布者或完整 Subject 要求。附件 README 中的签名发布文字与用户明确决策冲突，不采纳。

## 5. 实现结构

### 5.1 渐进迁移

新增结构按职责组织，名称可随现有文件进一步核实：

```text
src/styles/                 新语义 Token、主题/皮肤、局部布局样式
src/components/ui/          Button、表单、状态、Dialog、Drawer 等共享控件
src/components/shell/       Topbar、Statusbar、命令面板、导航上下文
src/components/account/     沿用账号功能组件并替换其视图
src/components/onboarding/  新路线状态机与四步视图
src/pages/                  沿现有页面逐个迁移
electron/                   在现有服务边界补窗口/会话/任务能力
canvas-v2/                  沿用独立画布应用
```

首批建设约 12–16 个高复用基础控件，按页面接入逐步覆盖全部 46 项，不为组件清单一次性制造大量空壳。复合组件通过语义 props 限制外观，支持可访问名称、testId、受控状态和明确错误；需要布局扩展时通过容器与已登记变体解决。

UI 样例页用现有 Vite + Playwright 测试方式建立，默认不额外引入 Storybook、状态库或整套 CSS 框架。保留 Lucide；品牌缺口确认资源与许可证后再按需引入图标包。

`src/navigation.ts` 仍是页面注册入口；Provider 身份与顺序沿 `catalog.ts`、`provider-registry.ts` 扩展，不新建互相竞争的表。工具桌面入口和 CLI 入口可以不同，但 Codex 配置仍共用同一 Provider。

新页面通过现有 props/控制器及必要的 feature hooks 获取业务状态；不在每个页面另造 IPC 和请求缓存。旧 CSS 按已迁移引用逐段淘汰，最终无旧视觉依赖后再清理；迁移中用作用域和变量别名避免全局相互覆盖。

公告复核真实接口来源，以稳定公告 ID 持久化已读状态；加载失败和无公告各自呈现，不能复制原型的优惠、服务时间或未读数量。全局告警统一确定优先级、去重和关闭规则，帮助与客服复用真实支持入口，保持原任务的返回上下文。

### 5.2 窗口与缩放先做技术验证

以 1280 逻辑设计宽和桌面版信息层级为基线，保留列内弹性、页内纵向滚动和表格自身横向滚动。正文不使用 vw 等随窗口变动的字号。

附件的 `setZoomFactor` 整体缩放先做独立 POC：使用 Electron 原生内容边界 DIP，澄清“内容区宽”指整个 WebContents 还是中央页面，避免扣两次侧栏或重复乘系统 DPI；验证 70% 下实际文字和点击目标是否可用。“100%”相对自动倍率的定义也须在控件语义中明确。

POC 检查最小窗口、125%/150% 系统缩放、多屏换屏、最大化恢复、弹窗定位与画布坐标。若最低整体倍率不可读，方案建议提高可读下限并允许局部滚动，不靠进一步缩小文字消除溢出。最终数值在本步骤冻结后才迁移全应用。

## 6. 需要新增的真实能力

### 6.1 Key 自动准备

设计要求注册时服务端自动创建四把 Key，客户端只拉取并按选中工具写入。当前 `electron/new-api-client.ts` 的 `provisionCliKey` 会查找并在缺失时创建；`account-cli-provisioner.ts` 已支持成功/失败结果清单。

实施前核实服务端在注册、重登、老账号、部分分组缺 Key 时的真实契约。服务端保证成立后再调整客户端：先拉取、逐工具写入、回读验证、失败仅重试未完成项。若服务端尚未保证，保留现有幂等补齐能力并如实呈现，不能把“注册后四把已齐”提前写成成功。此项需测试环境或服务端契约证据，不由本 UI 任务修改 new-api。

### 6.2 多账号

现有 Key 和部分资产已按 userId 隔离，但 `account-session-store.ts` 仍是单账号登录存储。需要新增按站点 + userId 的加密会话索引、目标账号预验证、活动账号切换及失败保持原账号。

切换时取消或隔离旧请求世代；订单、Key、草稿、用量和任务按稳定账号身份保存。先完成会话切换再逐工具同步，部分同步失败应给出清单。设备级外观/窗口设置与账号级消费偏好明确分开。只在这一项引入实际存储变化时设计迁移、备份和回滚，不为换皮伪造整套数据迁移。

### 6.3 托盘与关闭保护

现有主窗关闭会关闭画布和付款窗口；画布卸载保存也不能视为已等待落盘。增加可等待的统一关闭协调器：检查草稿/保存/安装/付费任务，按用户选择等待、实际取消或保留后台任务，结果确认后再隐藏/退出。保存失败和取消关闭必须保留窗口。

托盘先用 Electron 原生 Tray + Menu 实现打开、余额摘要、已装工具、充值、更新、设置、退出。原生菜单的颜色、圆角和精确尺寸由系统控制，不承诺像浏览器原型一样逐像素还原；需要完全自绘时作为额外范围单独评估。托盘不可用时不隐藏到无法找回的位置。

外部深链需注册及冷/热启动解析，限制允许的动作和参数；支付回跳只触发订单查询，不直接确认到账。内部 `xingmang://` 资源协议并不等于已有外部深链接入。

### 6.4 逐项设置、通知、代理与任务控制

已有设置用 `app-settings.ts` 的 patch 与串行原子写扩展，每字段保留 confirmed/attempt/requestId；快速切换时最新意图胜出。外观即时预览与保存失败分开处理。

启动项、代理、企业证书、通知和默认终端要逐项核对真实适配能力；没有能力时显示明确状态与下一步，不放置点击后假成功的控件。代理不能仅改 Electron renderer 而漏掉主进程 Node 请求，也不能破坏现有下载 URL、重定向和凭据边界。

安装、诊断和更新目前并非都有公开取消 API。需要为支持取消的任务增加 ID、进度、允许动作和终态；不可中断阶段如实说明。付费图片/视频“停止等待”不等于远端取消或退款；已拿到 taskId 的视频优先恢复查询，不自动重新提交扣费请求。

### 6.5 画布与扩展的能力保护

画布保留 React Flow、当前项目格式、全部节点、素材索引、运行记录和视频恢复。附件的四节点和 `xingmang-canvas-demo` JSON 只用于理解交互，不能当迁移目标格式。

MCP 的 SSE、OAuth 参数和预设按 Provider 适配器支持程度接入；插件市场目前不是所有 Provider 都支持，不能简单复制下拉选项。所有启停/卸载/恢复在确认后仍校验 capability 与只读状态。

## 8. 多 agent 分工与集成方式

使用 3 个实现 agent + 1 个集成负责人：

| 角色 | 负责边界 |
|---|---|
| 集成负责人 | Token/组件契约、`App.tsx`、导航装配、IPC 三件套、评审和最终回归 |
| Agent A | 欢迎/认证/引导/首页/配置视图 |
| Agent B | 账号/订单/聊天/扩展/记录等页面，按批次移交 |
| Agent C | 窗口/设置/多账号/任务控制和对应主进程测试 |

独立复核由完成阶段的 agent 交叉审查。共享样式、`App.tsx` 与 IPC 合约/preload/handler 注册由单一负责人编辑；各 agent 先提交所需接口，不并行改同一公共文件。禁止把原型静态状态机直接粘入业务层。
