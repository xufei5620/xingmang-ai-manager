# 服务状态文件（service-status.json）与坏版本回退

更新目录上放一份小文件，发布者不用发版就能让已装好的客户端：说一句「服务正在维护」、
撤回一个坏版本（还没升的人不再升，已经升上去的人可以退回）、让新版本先只推给一部分电脑、
要求低于某个版本的人先更新再用（强制更新）。
客户端的读法在 `electron/service-status.ts`，界面在 `src/renderer-v2/features/app/MaintenanceNotice.tsx`。

只有 **0.2.10 及以后**的客户端认这份文件，更早的版本不受影响。三件事都可以在 GitHub 上点按钮完成，不用手改文件。

## 它在哪

和更新清单 `latest.yml` 放在同一个目录：

```
https://updatesnew.shenfengwl.fun/xingmang-manager/service-status.json
```

（R2 桶里的路径是 `xingmang-manager/service-status.json`。）测试包如果打包时换了更新地址，
它读的是那个地址下的同名文件，可以拿来演练。

0.2.18 起，Windows 正式版在星芒账号走直连时，更新清单和这份文件都改从服务端的直连地址读
（`https://xm-direct.solov.cc/xingmang-manager/service-status.json`，见 `electron/update-feed-route.ts`）。
那边给的应该是同一份内容，我们只改上面那份；改完两边都打开看一眼，对不上就请服务端查那边有没有缓存（推测：没核实过那边会不会缓存）。

## 客户端怎么用它

- 启动时在后台读一次，之后每 15 分钟读一次；正在维护时改成每 5 分钟一次，好让维护一结束提示就消失。
- 读不到（没这个文件、没联网、超时、内容不是 JSON）一律当作**没在维护**，不报错、不挡启动。
- 打开维护时，右上角出一条「服务正在维护」：先是你写的那句话，后面固定跟一句「这不是你这边的问题，
  不用重新登录，也不用改任何设置，维护结束后会自动恢复」。没写那句话时用默认说法。
- 没登录也看得到：欢迎页右上角有，登录框里也有一份（登录框会盖住角落）。
- 用户可以关掉角落那条；你改了说法（比如把预计恢复时间从 22:00 改成 23:00）它会再出现。
- 写了结束时间的话，过了这个时间客户端自己当维护结束，防止维护完忘了关。

## 怎么打开、关闭（推荐：在 GitHub 上点）

1. 打开仓库的 **Actions** 页，左边选 **service-status**，右边点 **Run workflow**。
2. 「维护提示」选 **on: 打开** 或 **off: 关闭**。
3. 打开时可以填：
   - 「给用户看的一句话」：例如「服务升级中，预计今晚 23:00 前恢复。」最多 200 字，只写一句普通的话，不要放链接。
   - 「结束时间」：北京时间，写成 `2026-09-24 23:00`。可以留空。
4. 点绿色的 **Run workflow**。
5. 等它停在 **Waiting**，点进去 → **Review deployments** → 勾 **release** → **Approve and deploy**。
   （和正式发版用的是同一个环境、同一组 R2 凭据，所以每次都要你点这一下。）
6. 跑绿就生效了，日志最后一步会写「客户端下一次读取就会看到这一份」。

留空的项不会动线上已有的内容：比如只想关维护，选 off 其余都不填就行。

如果它红在「线上的状态文件读回来不是有效的 JSON 对象」：多半是缓存或网站临时回了一张网页。它故意停下，
因为照空白重建会把撤回名单和分批放量一起抹掉。过几分钟重跑；还不行就用浏览器打开上面那个地址看看，
内容真坏了就按下面「备用」一节在 Cloudflare 后台传一份好的。回滚（rollback-release）读同一个文件，也会同样停下，这时线上什么都还没改。

**核对**：浏览器打开上面那个地址，看到的就是客户端读到的内容。

这个按钮要 release 环境里已有这四个 secret：`R2_ACCOUNT_ID`、`R2_BUCKET`、`R2_ACCESS_KEY_ID`、
`R2_SECRET_ACCESS_KEY`（正式发版用的就是它们）。缺哪个，第一步就会红并写出缺的名字。

## 备用：直接在 Cloudflare 后台改

GitHub 用不了的时候：

1. 在电脑上新建一个文本文件，命名为 `service-status.json`，内容照下面「文件长什么样」写，存成 UTF-8。
2. Cloudflare 后台 → **R2** → 你的桶 → 进 `xingmang-manager` 文件夹 → **Upload**，选这个文件，覆盖同名文件。
3. 浏览器打开上面的地址核对。如果看到的还是旧内容，多半是缓存，等几分钟再看。

关维护最简单的办法是把 `"active": true` 改成 `false` 再传一次（或者直接删掉这个文件）。

## 坏版本回退

发出去的版本有严重问题时，**一键回退**：

1. Actions → **rollback-release** → **Run workflow**，「退回到哪个版本」填上一个好版本。下面拿「线上是坏的 `0.2.11`，退回 `0.2.10`」举例。
2. 点 Run workflow，停在 Waiting 时 **Review deployments** → 勾 **release** → **Approve and deploy**。
3. 它会依次做：
   - 先核对：`0.2.10` 的备份清单在不在、确实比线上旧，再把它要的每个安装包从更新目录完整下载一遍，大小、指纹、blockmap 都要和清单记的一字不差。哪条不对就停下，线上什么都不改。
   - Windows 那份清单还要过更新包签名（见 `docs/RELEASING.md`「更新包签名」）：备份本来带签名的验签；加签名之前发的老版本，要和 GitHub Release 上同版本的安装包逐字节对上才补签，对不上就停下。GitHub Release 上找不到那个安装包时照样退回，但认签名的新客户端会停在被撤回的版本上（日志里有一条黄色提示）。
   - 在状态文件里把线上那个版本（`0.2.11`）加进撤回名单。从这一刻起，还没升上去的人不会再被推送 `0.2.11`。
   - 把更新清单换回 `0.2.10` 的备份，再完整复核一遍更新目录。
4. 已经装了 `0.2.11` 的人，下次检查更新（启动时、每 3 小时、或自己点）会看到「建议退回稳定版本」「发布者撤回了 0.2.11。建议装回 0.2.10」。
   之后和平时的更新一样跟着「自动更新」开关走（0.2.12 起默认开着）：开着的在后台下好，退出时或下次打开时自动装回去
   （Windows 会弹授权窗口）；关着的要自己点下载、再点「重启安装」。（按 `electron/updater.ts`、`electron/auto-update-install.ts`
   看是这样，往回装这一路没在真机上演过。）

要知道的几件事：

- 备份是正式发布时自动存的（`manifests/<版本>/latest.yml`、`latest-mac.yml`，Linux 对外发过以后还有 `latest-linux.yml`、`latest-linux-arm64.yml`）：每次发新版，都会先把线上那一份按它的版本号存起来，
  新版本自己也存一份。所以只能退回到**这个功能上线（0.2.10 发布）之后还在线上待过**的版本。
- 客户端最低只肯退到 **0.2.9**（`electron/updater.ts` 的 `rollbackFloorVersion`）：万一更新目录被人拿到，也没法借退回把大家装回更老、有已知问题的版本。以后某一版修了安全问题，把这个下限抬到那一版。
  这个下限只在客户端里：rollback-release 本身不查它，填一个比下限还旧的版本照样会跑完（见下面 `0.2.10` 那一段）。
- 能不能退，看下面「现在能退到哪」。
- 退回只对 **0.2.10 及以后**的客户端有效。更早的客户端不认撤回名单，会一直停在当前版本，直到出了更高的修好的版本。
- 能修的话，优先发一个更高的修好版（比如 `0.2.12`）：撤回名单里的人会直接被推到它，不用退回。退回是修好版来不及时的止血办法。
- 退回装的是旧程序，新版本改过的本机数据格式旧版本可能不认识。发版说明里写了「数据迁移」的版本，退回前先在自己电脑上试一次。
- 各平台分开看：比如只有 Windows 升到了坏的 `0.2.11`、Mac 线上还是 `0.2.10`，退回 `0.2.10` 时 Mac 那一半直接跳过（日志写「线上已经是 0.2.10，这个平台不用退回」），只退 Windows。某个平台线上比要退回的版本还旧，照样第一步就停。
- Linux：线上没有 Linux 清单（开关没打开过，见 `docs/RELEASING.md`「Linux 开关」）时直接跳过。对外发过以后 x64 和 arm64 两份清单一起退，版本号和 Windows / Mac 共用，撤回名单也共用。Linux 最早只能退到它**第一次对外发的那一版**：再早的版本没有 Linux 的包和备份，那次回滚会对 Linux 报一条黄色提示、Linux 保持不动，别的平台照样退。
- 退回之后，**别再重跑那个坏版本的 publish-release**：发布前会读一次状态文件，版本在撤回名单里就停下，线上什么都不改。修好了请提升版本号再发；真要让它原样重新上线，先在 service-status 的「撤回的版本」填 `-0.2.11` 把它移出名单。
- 修好版发出去后，`0.2.11` 留在撤回名单里就好，不用删：停在它上面的人不受分批放量限制，会最先拿到修好版。
- **service-status、rollback-release 和正式发布的上传那一步会排队，一次只跑一个。** 它们都是先读线上、再写回去，
  同时跑的话后写的会盖掉先写的。所以某一条停在 Waiting 或 Pending 时，先看是不是另一条正在跑或正等你批准：
  等它跑完（或把它 Reject 掉）再批这一条。注意 GitHub 同一组里只留一个排队的：已经有一条在排队时再点一条，
  先排的那条会被取消（什么都没写），要的话重新点一次。正式发布只有最后上传那一段排队，前面出包不受影响。

也可以只撤回、不换清单：在 **service-status** 里「撤回的版本」填坏的那个版本号（比如 `0.2.11`）。这样没升的人不会再升，已升的人等修好版。
但撤回名单只有 0.2.10 及以后的客户端认：还停在 0.2.8 或更早的人照样会被推送坏版本，要挡住他们只能把更新清单换掉（也就是跑 rollback-release）。

### 现在能退到哪

截至 **2026-10-08**：正式发过的是 `0.2.10`、`0.2.12`、`0.2.13`、`0.2.14`、`0.2.15`（GitHub 上各有 tag 和 Release），线上是 `0.2.15`。
`0.2.9`、`0.2.11`、`0.2.16`、`0.2.17` 都没有正式发过（只出过测试包，或者攒进了下一版），更新目录里没有它们的清单，也就没有备份。
每次正式发布都会把发布前线上那一份和新版本自己那一份存进 `manifests/<版本>/`，所以上面每个正式版本都应该有备份
（推测：沙箱读不到更新目录，没逐个打开核对；填错了也不要紧，rollback-release 第一步发现没有备份就停下，线上什么都不改）。

| 线上是坏的 | 「退回到哪个版本」填 | 要知道的 |
|---|---|---|
| `0.2.15`（现在） | `0.2.14` | |
| `0.2.18`（下一版） | `0.2.15` | 0.2.15 的 Windows 备份清单没有更新包签名，工作流会拿 GitHub Release 上的 0.2.15 安装包逐字节对上后补签（那个安装包在，2026-10-08 查过），0.2.18 的 Windows 客户端才肯装回去 |
| 以后的版本 | 上一个正式发过的版本 | 不能低于客户端下限 `0.2.9` |

填一个比下限还旧的版本（比如 `0.2.8`）也会跑完，但效果只是**撤下**坏版本：更新清单换回旧版、坏版本进撤回名单，挡住还没升上去的人
（包括不认撤回名单的 0.2.8、0.2.9）；已经装了坏版本的人不会被退回去，他们会看到「这个版本有已知问题」「修好的版本准备好后，这里会提示你更新」，
停在原地等修好版。`0.2.10` 刚发出时只能这么做，因为当时它的上一版 `0.2.9` 没有正式发过。

## 分批放量

新版本先只给一部分电脑，没问题再全放：

1. **发布之前**，在 **service-status** 里「分批放量」填 `0.2.11 20`（版本号、空格、百分比），跑完。
2. 再照常发布 `0.2.11`。自动检查更新时只有大约两成电脑会看到它；用户自己点「检查更新」的不受限制。
3. 观察一段时间没问题，再跑一次 service-status，「分批放量」填 `0.2.11 100` 或 `none`，全部放开。观察时想看新版本铺开了多少，跑一次 update-feed-stats（见下面「看各版本有多少人在用」）。

一定要先设放量再发布：反过来的话，发布到设置之间检查更新的人都会拿到新版本。哪台电脑在「两成」里是固定的，
不会每次检查换一批人。

放到一半发现问题、想先停住：「分批放量」填 `0.2.11 0`。之后自动检查一个都不推，用户自己点「检查更新」的照样拿得到，已经装上的不受影响。
修好了填回 `0.2.11 20` 接着放；问题严重就改用上面的撤回或回退。

想先只给少数人试、观察后再全放（手动灰度）：发布前填 `0.2.11 0`，发布后自动检查谁都不推，只有自己点「检查更新」的人拿得到；
观察没问题再填 `none`。这段时间里撤回名单上的版本、低于「最低版本」的电脑、不读这份文件的 0.2.8 和 0.2.9 照样会拿到新版本，
从安装教程页下载的新客户在 `cos-sync` 跑完后也是新版本。

## 强制更新（最低版本）

某个旧版本有严重问题、必须让大家先升上来时用。**只有 0.2.11 及以后的客户端认这一项**：
0.2.8、0.2.9 根本不读这份文件，0.2.10 读但不认这一项，它们照旧只在首页挂一条能关掉的「新版本可以安装」。

**打开**：

1. 先确认要求的那个版本已经正式发布了（比如要大家至少到 `0.2.13`，就先把 `0.2.13` 发出去）。
2. Actions → **service-status** → **Run workflow**，「最低版本」填 `0.2.13`，其余留空。
3. 点 Run workflow，停在 Waiting 时 **Review deployments** → 勾 **release** → **Approve and deploy**。
4. 跑绿就生效。版本低于 `0.2.13` 的客户下一次读这份文件（打开软件时，或开着的最迟 15 分钟）就会看到。

**客户看到什么**：整个界面上盖一层提示，关不掉（没有叉，按 Esc 也不行）：

- 标题「这个版本需要更新后才能继续用」
- 正文「为了让工具和账号正常工作，请先更新到 0.2.13 或更新的版本。点「立即更新」，新版本会自己下载并装好，中间会重启一次，账号和设置都会保留。」Windows 上多一句「装的时候如果弹出「是否允许更改」，点「是」。」
- 一行「现在是 0.2.12，将更新到 0.2.13」
- 按钮只有「立即更新」和「联系客服」。点「立即更新」后按钮依次变成「正在检查新版本…」「正在下载 42%」「正在重启安装…」，装好自动重开。
- 哪一步失败了，标题、原因和按钮与更新页、首页气泡同一套：「检查更新失败 / 下载更新失败 / 安装更新失败」+ 原因，按钮变成「重试 / 重新下载 / 重新安装」，并多出一个「打开下载页」（打开 GitHub 上最新版的下载页，客户自己下安装包装）。

**不会把客户困住的几道保护**：

- 最低版本不能填得比线上正在发的版本还高：工作流会先读线上各平台的更新清单（Linux 两个架构各一份，没发过的平台跳过），高了就红，报「最低版本 … 比线上正在发的 … 还高」，线上什么都不改。
- 万一还是出现了找不到新版本的情况（比如新版本被撤回），客户端检查后发现没有可装的新版本，就不拦，客户照常用。
- 这份文件读不到、「最低版本」写错（比如写成 `0.2`、`latest`、`0.2.13-beta`），都当作没有最低版本。
- 低于最低版本的电脑不受分批放量限制，检查时一定能拿到新版本。

**取消**：同样跑一次 service-status，「最低版本」填 `none`。客户端下一次读到就不拦了。

**在测试电脑上演一遍**（不影响客户）：要一个带这段代码、但版本号比线上低的测试包。比如线上已经发了 `0.2.11`，
从版本号还是 `0.2.10` 的分支出一个测试包装到测试电脑上，「最低版本」填 `0.2.11`。真实的 0.2.10 客户不认这一项，
0.2.11 客户不低于它，只有这台测试电脑会被拦住。演完填 `none` 取消。

## 看各版本有多少人在用

Actions → **update-feed-stats** → **Run workflow**，「统计最近几天」默认 7，点 Run workflow。不用批准，一两分钟跑完。
点进那条运行，结果在 Summary 页上：各版本占全部电脑的比例（Windows、Mac、Linux 分开列），下面再附一张按请求算的对照表。

**怎么数的**：0.2.10 起的客户端打开时、开着时每 15 分钟读一次这份 service-status.json，请求里带着自己的版本号
（Electron 默认的 User-Agent，里面有「星芒AI管理工具/0.2.15」）。工作流拿只读令牌查 Cloudflare 的访问统计，把这些请求
按版本、系统和来源 IP 归拢，每台电脑只算它这段时间里最后一次读时的版本。来源 IP 只在运行时拿来去重，不写进日志和结果。

**只有比例，没有台数**：仓库是公开的，运行页谁都能看，写台数等于告诉别人有多少客户。

**看不到、不准的地方**：

- 0.2.8、0.2.9 不读这份文件。
- 0.2.18 起 Windows 走直连线路的电脑从 `xm-direct.solov.cc` 读，那部分只在服务端日志里，这里看不到。
- 同一个网络出口下的几台电脑算一台，换过网络的电脑会算成几台。
- Cloudflare 只留最近一段时间的统计，填的天数比它留的多时只统计它留着的那段，Summary 页上会写明。

**令牌**：仓库 Secrets 里的 `CLOUDFLARE_ANALYTICS_TOKEN`（Settings → Secrets and variables → Actions → Repository secrets，
不在 release 环境里）。运行报「令牌被 Cloudflare 拒绝」就是过期或被删了，在 Cloudflare 右上角头像 → My Profile → API Tokens →
Create Token → Create Custom Token 重建：Permissions 两行 Zone｜Analytics｜Read 和 Zone｜Zone｜Read，Zone Resources 选

## 文件长什么样

```json
{
  "maintenance": {
    "active": true,
    "message": "服务升级中，预计今晚 23:00 前恢复。",
    "until": "2026-09-24T15:00:00.000Z"
  },
  "badVersions": ["0.2.10"],
  "rollout": { "version": "0.2.11", "percent": 20 },
  "minimumVersion": "0.2.11"
}
```

- `maintenance.active`：只有写成 `true`（不带引号）才算在维护。
- `message`：可省略。控制字符会被去掉，超过 200 字的部分客户端不显示。
- `until`：可省略。必须带时区（上例是 UTC，等于北京时间 24 日 23:00）。
- `badVersions`：撤回的版本，写成 `["0.2.10"]`。只认 `0.2.10` 这种写法。
- `rollout`：分批放量，写成 `{ "version": "0.2.11", "percent": 20 }`。
- `minimumVersion`：最低版本，写成 `"0.2.11"`，只认三段数字。手改文件时同样不要填得比线上正在发的版本高。
- 其他字段客户端不认，留着也没关系；GitHub 按钮会多写一个 `updatedAt` 记录改动时间。
