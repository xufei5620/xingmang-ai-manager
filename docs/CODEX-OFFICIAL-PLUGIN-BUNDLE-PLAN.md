# ChatGPT 官方插件随包预置与原生全量可见方案

日期：2026-10-04。状态：方案文档，待实施；本 PR 不发布客户端功能。

## 1. 用户要得到的结果

> 用户安装星芒 AI 管理工具后，不需要自己连接加速、不需要到插件管理页点下载、不需要敲命令。打开 ChatGPT 桌面端，在它原生的插件页面就能看到目标版本的全部官方插件，并能选择安装。

本方案采用**完整资源随星芒安装包交付、当前用户自动初始化、ChatGPT 原生页面展示与安装、后续国内通道自动更新**。首次可见不能依赖客户机再访问 GitHub 下载资源。

交付平台同时包括 **Windows x64、macOS Apple Silicon arm64、macOS Intel x64**，Mac 不是以后再补的附加项。本文“ChatGPT 桌面端”指用户当前使用的、承载 Codex 功能与原生插件页的官方桌面产品，也就是本仓代码与界面里说的「Codex 桌面端」（`electron/codex-desktop-service.ts`；Mac 上应用名就叫 ChatGPT）；Windows 研究对象包标识是 OpenAI.Codex，macOS 需独立确认对应官方 bundle 与内置运行时。其他独立客户端不能直接套用本研究的目录机制。

“预置”指资源已经在电脑上；不代表自动安装并启用所有插件。默认由用户在 ChatGPT 原生页决定安装，插件所需的账号登录、授权和运行环境另行显示。星芒精选和第三方扩展不替代本次全量官方目标，也不作为本次第一版范围。

### 本次必须明确的限制

研究已经证明本地插件的发现和安装链路，但尚未证明 API Key 模式能显示参考 ChatGPT 账号下的全部官方云端条目。当前 API 官方目录与完整目录不同，部分云端查询还要求 ChatGPT 登录。**这是阶段 0 必须解决的验收阻断，不能把“API 精选能显示”写成“全部官方插件已显示”。**

同样，官方清单有远程 Git 来源和许可受限的资源。只打包公开仓库的 local 子目录不能完成全量交付。下面将这些情况列为具体交付物、技术验证和发布门禁，不能用“用户再开加速试试”收尾。

## 2. “全部官方插件”的准确口径

以目标 ChatGPT 桌面版本和本次指定的参考电脑／官方目录为基线，生成固定版本的 `catalogs.lock.json`。列表按插件身份逐项保存，不能只比较数量，也不能用本机已经安装的缓存数代表全部市场。Windows、Mac arm64、Mac x64 各有独立的 U/V/I/R 与桌面版本记录，不能用 Windows 清单或截图代替 Mac。

| 集合 | 内容 | 如何核对 |
| --- | --- | --- |
| U：目标官方条目 | 指定版本官方公开目录，加上参考原生页可见的官方自带／云端条目 | 保存来源、canonical ID、版本、平台、登录方式、可见分类，逐项冻结 |
| D：已经准备的文件 | U 中可合法分发、可由本地安装的插件完整实体 | 文件清单、来源 commit、SHA-256、解压后大小 |
| V：原生页面实际可见 | 全新测试用户在指定版本、登录方式下实际看到的条目 | 原生页面证据加只读目录核对，按 canonical ID 对照 U |
| I：可安装 | 原生安装完成且读回已安装的条目 | 包文件、安装结果、缓存内容、启用状态分别核对 |
| R：可运行 | 依赖就绪、授权完成后能执行声明能力的条目 | 按插件的本地能力／远程能力独立验收 |

全量可见验收要求 `U - V` 为空。API Key、ChatGPT 登录、未登录分别记录；登录方式不能成为悄悄缩小 U 的理由。原生允许显示但需登录的条目可以保留真实的“需要登录／不可用”状态，不伪造权限或绕过认证。

如果某条只存在于需 ChatGPT 身份的云端服务、API Key 原生页根本无法展示，则记录确切缺项与原因，并将“API Key 模式全量可见”判为未通过。后续只有在官方支持的本地市场方式可以展示该公开条目、且不伪装官方身份或绕过权限时，才可补足；否则该目标仍是产品阻断，需要另行明确范围，不能在实现或宣传中自动改成“支持的部分”。

“官方”指上游官方目录收录，不代表所有作者均为 OpenAI。保持原作者、上游链接、商标和授权信息。个人插件、其他厂商市场与当前项目的私有插件不并入 U。

## 4. 资源从哪里来，如何进入安装包

### 4.1 在构建端准备，不让客户临时拼包

新增构建任务从固定上游 ref 解析 U，下载所有需要的目录和插件实体，生成可追溯的完整包。资源构建在维护者／CI 环境完成，使用现有网络下载防护；它不把插件指令当作构建命令执行，不运行插件 hooks 或任意安装脚本。

必须包含：两个官方市场清单、清单引用的完整本地插件实体、必要的展示资产、所有允许本地安装的远程来源实体、许可与来源记录。不能只带一份 JSON、空目录或磁盘上碰巧已有的安装缓存。

ChatGPT 本来随程序提供的 bundled/runtime 组件由官方安装包负责。只核对它们在目标版本是否存在、是否按原生规则可见，不从开发者个人缓存复制到星芒充数；需要额外分发时必须单独证明来源与许可。

### 4.2 资源包结构

拟新增 `bundled-catalog/codex-official-plugins/` 作为构建输入描述目录；实体产物不入 Git，构建阶段生成后通过 `electron-builder.config.cjs` 的 `extraResources` 打入客户端：

```text
resources/codex-official-plugins/
  bundle.json                 # 分发包版本、兼容范围、计数、整体摘要
  catalogs.lock.json          # 冻结的 U 集合及每项交付依据
  payload.tar.gz              # 完整实体，固定相对路径
  files.sha256                # 文件级摘要
  THIRD-PARTY-NOTICES.txt      # 原作者、许可证、来源
```

`bundle.json` 至少包含 schemaVersion、bundleVersion、upstreamRepository、upstreamCommit、desktopVersionRange、runtimeVersionRange、platforms、catalogDigest、archiveSha256、compressedBytes、expandedBytes、fileCount、pluginCount。逐项清单另含 canonicalPluginId、nativePluginId、nativeMarketplaceName、upstreamSource、resolvedCommit、deliveryKind、requiredFiles、licenseEvidence、needsAccount、installDependencies、runtimeDependencies。

canonicalPluginId 表示原官方身份；nativePluginId/nativeMarketplaceName 表示实际分发入口。独立派生市场可能改变原生 selector，U/V 对照必须通过经验证的显式映射完成，不能同时假定换市场与原生 ID 不变。映射要覆盖去重、已安装识别、启停、卸载和升级，不产生两份难以区分的同一插件。

包版本与上游 Git SHA 分开。派生资源布局、重写来源或补充实体时，必须记录派生清单和原始清单的摘要，不能把派生内容伪称为原始官方 commit。

### 4.3 三个 Git 远程来源不能遗漏

研究样本中的 crowdstrike-falcon-foundry、crowdstrike-falcon-fusion、qodo 仍指向远程 Git。构建端应固定它们的实际 commit 并完整准备；下载完并不意味着原生安装一定命中这些文件。

阶段 0 按以下顺序验证交付方法：

1. **受支持的本地 source 映射**：在经过兼容验证的派生分发清单中，把这些来源映射到包内实体；保留 canonical ID、原作者、版本和来源证明。派生状态对维护者明确，不绕过原生账号限制。必须验证原生分类、安装、更新与去重行为。
2. **原生已有缓存复用**：仅当固定版本源码与实测证明原生支持命中该缓存且不再次 clone 时采用；记录准确缓存键和失效规则。不能手写一次目录就认为支持。

这两个方法均未验证完成。未找到受支持方式时，将相关条目标为交付阻断，不能退回客户手动开加速，也不能把残缺包标为 full。新上游引入 Git/npm 等来源时适用同一规则。

### 4.4 分发资格逐项落实

每个实体都要有可再分发依据。研究中已发现 manifest 标为 Proprietary 的包，公开可下载不自动等于可以随星芒再分发。缺少依据时列出具体条目，取得许可或官方支持的交付方式后再进入全量包；不能静默删掉再宣称全部。

本阶段只建立资料与发布门禁，不在文档 PR 中下载全部闭源资源或对外分发插件代码。

## 5. 安装星芒时自动准备到正确用户目录

### 5.1 安装包内的资源与用户目录分别处理

资源实体在星芒受信任的应用资源目录内，只读保存。向 Codex 用户目录发布由当前登录用户权限的主进程／一次性初始化助手执行，复用 `safe-local-data`、`bounded-*`、可信解包和原子写入。

Windows 当前 NSIS 为 perMachine。不能由提权安装器直接把 `~/.codex` 当成客户目录：UAC 可能使用另一管理员账号。实现必须验证安装发起者 SID、交互用户身份和实际目标 root；在同一客户身份下运行初始化，禁止管理员凭据与用户可控路径跨边界混用。

Windows 安装完成阶段自动运行一次性准备流程，不要求用户额外打开星芒插件页。准备流程与是否打开星芒主界面的选项分离。若无法安全恢复原交互用户身份，则该安装场景验收失败，不写管理员 profile 作为替代。不能扫描并写入所有 profile。

其他 Windows 用户从未启动星芒就直接开 ChatGPT 的情况，现有安装器／星芒启动钩子没有执行者。P0 必须验证受支持的按用户初始化或原生机器级读取机制；未解决前此多用户场景仍不达标，不能从用户 A 成功推断用户 B 自动可用。不为掩盖这个缺口擅加全机 profile 写入或常驻代理。

macOS 使用当前用户正常首次启动阶段自动准备；具体机制见 5.4。Linux 不包含当前无原生启动支持的承诺，能力判断服从 `platformCapabilitiesFor`。

### 5.2 必须支持直接打开 ChatGPT

准备结果在用户目录持久存在。完成一次准备后，即使星芒退出、电脑重启，用户直接点 Windows 快捷方式或 Mac Finder/Dock/Spotlight 中的 ChatGPT 也能读到资源，不依赖星芒持续运行或临时代理。

Windows 安装结束、两平台星芒首次启动、星芒升级后检查、安装／升级 ChatGPT 完成、星芒打开 ChatGPT 前检查，统一调用一个幂等准备协调器。Windows 安装结束即准备是第一条入口，Mac 正常首次打开星芒时自动准备；不能只实现“通过星芒打开 ChatGPT”这一条钩子。

若安装星芒时 ChatGPT 尚未安装，先完成资源准备；后续星芒安装 ChatGPT 时确认版本与 root 并发布。用户另行安装未验证的新版本后，不能默认沿用兼容结论；下次检查报告兼容状态，不自动降级其软件。

### 5.3 Root 和版本对账

已有 `resolveCodexHomeContext` 统一星芒自己的 CODEX_HOME；它不是 Windows AppModel 激活后的 native root 证明。准备前核对当前用户、桌面实际版本、内置运行时、已确认的 native root。相对路径、错误环境变量、不同用户和非默认 CODEX_HOME 都有独立验收。

默认共享同一个用户 root。不能为插件功能悄悄另建一套 Codex 登录、会话或工作区配置；不能使用另一版本 PATH CLI 的成功输出来证明目标桌面已就绪。

### 5.4 macOS 双架构的完整路径

1. **随包**：Apple Silicon 与 Intel 两份 DMG、两份自动更新 ZIP 都携带资源。纯文本和静态资产可共用内容摘要；带原生依赖的实体必须按平台/架构分别准备，不能把 Windows exe 或 arm64 运行组件发给 Intel。每份最终 .app、DMG、ZIP 分别检查目录与摘要。
2. **首次初始化**：把 .app 拖到 Applications 只是复制文件，不会运行初始化。用户完成星芒正常的首次打开／账号配置时，后台自动发布插件资源；不增加“下载插件”操作。若要求“从未打开过星芒，仅拖入应用后直接开 ChatGPT 就就绪”，当前 DMG 分发没有执行入口，列为未满足场景，不能声称已有这个效果；此方案不偷偷改为 PKG 或新增安装守护程序。
3. **用户目录**：在当前 uid 下把可写 staging、状态、备份放到星芒既有 Application Support 数据目录，向确认过的 CODEX_HOME 发布。星芒 .app/Contents/Resources 和官方 ChatGPT .app 只读；不修改应用 bundle、不加 sudo、不降低来源和路径检查。
4. **默认 root 与直接启动**：Finder/Dock/Spotlight 不继承终端配置；默认使用原生默认用户 root。现有 `/usr/bin/open --env CODEX_HOME=…` 只影响新启动进程，不能证明以后从 Dock 打开还会用非默认 root。非默认 root 必须核对从 Finder 直接冷启动的实际结果；没有受支持的持久一致方式时，不能标就绪或改用户的全局 shell/launchd 环境补救。
5. **应用移动与只读位置**：处理 /Applications、~/Applications、移动/改名后的有效官方 app、从只读 DMG 运行以及系统临时转移路径。遵从已有应用移动引导；任何情况下都不把可写插件状态放入 .app 内。移动后重新发现并核对真实官方 bundle 与 runtime。
6. **已运行与更新**：已经运行的原生 app 保留旧环境和目录缓存，更新进入 staging，下次正常冷启动生效；无条件终止进程不是更新手段。保持星芒既定自签身份和双架构 ZIP 更新链，在签名前准备资源，签名后不修改 bundle；不为此引入另一套公证或签名方案。
7. **客户环境**：准备本地资源不能要求 Homebrew、Git、Node、Python、Xcode 或 Command Line Tools。需要 CLI 核对时使用已验证的桌面内置 runtime 或现有管理器解析结果，不把 shell PATH 当作可信安装证明。某个插件运行另有依赖时明确区分，不让它阻塞目录展示。

Mac 的最低系统支持沿用当前包配置（目前 macOS 13+），每次发布检查实际版本要求。Apple Silicon 和 Intel 均需要真实机器或等效原生测试环境，Rosetta 的一次成功不代替两种原生架构验收。相关现状见 [macOS 开发](MACOS_DEVELOPMENT.md)、[现有分发链](MACOS_FREE_DISTRIBUTION.md)。

## 6. 安全发布与状态判定

准备流程顺序：

```text
发现随包资源 → 核对兼容版本与实际用户 root
  → 核对整体/逐文件摘要与清单引用
  → 同卷 staging 有界解包 → 校验全部实体
  → 检查原生进程和其他写入者 → 原子发布 + 失败回滚
  → 独立读回目录与实体 → 记录已准备版本
```

沿用 `InstallationQueue` 的互斥和同 key Promise 复用；多进程安装／升级时还要有跨进程占用检测，不能以进程内队列当作全机锁。

复用现有路径、reparse、单链接文件、磁盘空间、解包数量与字节数限制。UI 不接受任意目录参数；主进程根据可信上下文定位 root。网络输入、摘要文件和压缩包均做有界解析，不执行包内代码。

对 `.tmp/plugins` 与 `plugins.sha` 保持两阶段事务和恢复记录。不要篡改 auth.json，不整份覆盖 config.toml，不改用户已有安装、禁用状态或个人 marketplace。新增注册确有必要时只修改受支持的对应键，备份并读回。

状态至少为：`unprepared`、`preparing`、`prepared`、`incompatible`、`blocked`、`repair-needed`。`prepared` 要求全部 D 实体存在且摘要匹配，不能只看 JSON 和 marker 存在；它也不是 V/I/R 已经通过的同义词。

渲染层只接收版本、计数、状态与中文修复提示；不返回凭据、原始插件环境变量值或未经脱敏的用户绝对路径。日志写失败阶段和脱敏原因，诊断不输出完整插件配置。

## 7. 已运行客户端、原生自同步和更新

### 已运行的 ChatGPT

插件目录写入不保证原生页面立即刷新，研究版本的查询缓存可达六小时。首次准备需要在原生读取目录前完成；已运行时不强杀、不注入 JS、不冒充另一客户端订阅其私有 RPC。

自动更新先准备到 staging；原生关闭后切换，下次冷启动生效。用户主动要求立即生效时才提示保存工作并正常重开。已有可用版本时更新失败继续使用旧版本；首次没有可用资源时说明“插件准备未完成”，正常聊天仍可使用，不能报告目标已完成。

### 原生也会更新官方快照

阶段 0 必须验证 native 启动同步、官方目录更新和用户安装与星芒准备并发发生的行为。不能仅靠循环覆盖 native 文件维持派生 source。

若采用派生本地映射，需要受支持、可持续的所有权设计：原始快照与星芒拥有的派生市场分开保存，或经实验证明原生兼容入口不会把映射还原。避免重复条目与身份冲突；如果只能靠手改原生程序或反复抢写保证覆盖，方案不通过。

### 后续版本更新

首次依赖随包基线，不依赖在线更新。新插件资源以独立包通过现有国内静态下载通道自动更新，包含版本、来源和摘要校验；外部包签名／可信摘要必须由现有受信任发布链或独立固定公钥保证，不能只信任同一被下载 JSON 中的哈希。

保留一个可恢复版本与一份未完成 staging，磁盘不足先报告空间，不能删用户插件或大范围清缓存。离线时沿用旧基线，状态明确显示基线日期，不能声称与不断变化的官方实时目录永远同步。

维护端发现官方目录变化后生成差异清单：新增、删除、版本变化、来源类型变化、权限与运行依赖变化。新基线通过逐项审核和兼容验收后才发布；安全撤回只处理星芒拥有的资源，不静默卸载用户自行安装的插件。

## 8. 用户看到的交互

首次安装：Windows 安装收尾、Mac 正常首次打开星芒时自动完成资源准备。插件准备无需额外操作。打开 ChatGPT 后，在原生插件页看到对应平台 U 的全部条目及其真实状态，按原生流程点击安装。

星芒最多显示“插件资源已准备”“正在准备插件资源”“插件资源需要修复”三个普通状态。失败时给一个修复动作和一句原因。不能引导普通用户自己设置 Git、代理、环境变量或手动拷贝目录。

资源随包不等于所有能力离线：第三方账号登录、MCP 访问、插件实际工作仍可能联网。准备完成、显示完成、安装完成和功能可用分别记录，面向用户在必要位置清楚说明，不把“需要账号”写成“下载失败”。

## 9. 存储和带宽预算

2026-10-04 本机只读样本（MiB，1 MiB = 1,048,576 bytes）：

| 范围 | 展开后 | gzip 级别 6 | 限定 |
| --- | ---: | ---: | --- |
| 本机完整公开目录已有文件 | 51.18 MiB | 23.05 MiB | 清单 65 项，3 个远程来源实体未包含；不是最终全量包 |
| 本机 API 清单对应 local 文件 | 25.15 MiB | 10.92 MiB | 本机快照为 49 项；不能与固定上游 50 项样本混用 |
| 官方桌面自带插件资源 | 46.75 MiB | 21.07 MiB | 已在官方应用内，原则上不重复分发 |
| 本机已缓存的 OpenAI 来源副本 | 107.00 MiB | 未压缩 | 存在跨市场内容重叠，不作为唯一分发包总量 |

此前“安装包增加 20～30 MB、预留 300～500 MB”是已有公开 local 资源的规划估算。包含远程实体、所有目标官方资源及安装期依赖后的最终包必须重新实测，不能把 23.05 MiB 宣称为全部官方插件最终下载大小。

构建输出压缩大小、展开大小与最大文件数；安装前按“现有资源 + 新 staging + 待保留备份 + 目标副本 + 文件系统余量”计算峰值。下载总量、安装副本和备份分别计数，避免把同一实体重复相加为唯一内容大小。

所有自动测试使用 fixture/mock，绝不对生产账号后端或模型发送请求。UI 集成使用干净测试用户和非生产凭据；插件安装测试不得执行来源不明 hooks。

| 场景 | 操作 | 必须看到的结果 |
| --- | --- | --- |
| 新电脑首次安装 | 阻断 GitHub/raw/codeload，关闭一切加速，安装星芒后直接开 ChatGPT | 无手动下载；原生 V 与锁定 U 逐项相符 |

| Windows 其他用户 | 用户 B 从未运行星芒，直接启动官方客户端 | 只有受支持的按用户初始化/机器入口验证成功才通过；用户 A 的结果不可复用 |

| 断电／空间不足 | 在解包、备份、两个发布步骤中断 | 可恢复旧目录，重跑幂等，数据不误删 |
| 离线／国内更新失败 | 随包基线已就绪，更新不可用 | 旧基线继续可见可装；不要求用户开加速 |

macOS 还必须独立执行以下矩阵，不能用 Windows 通过代替：

| Mac 场景 | 必须取得的结果 |
| --- | --- |
| Apple Silicon arm64 与 Intel x64，各自全新用户 | 正常首次打开星芒后，无手动插件下载、无加速，原生 V 对齐各自 U |
| 禁止 GitHub、无 Git/开发工具/终端 PATH | 本地目录准备与全部可本地交付文件安装成立 |
| Finder、Dock、Spotlight 与重启后启动 | 默认 root 持续一致，星芒退出仍可发现与安装 |
| 非默认 CODEX_HOME，原生先开与后开 | 按实际 root 核对；不能把 open --env 的一次成功外推为 Dock 持久成功 |
| /Applications 与 ~/Applications、应用移动/改名 | 官方身份仍校验，插件数据不跟着只读 bundle 路径失效 |
| DMG 只读启动、临时转移路径、未做正常首次打开 | 给出准确未准备状态；仅拖 .app 不冒充初始化成功 |
| 两份 DMG 与两份 ZIP 的更新、断网、回滚 | 每个产物含正确资源；签名与更新身份连续，旧可用资源保留 |

完成条件不是“文件夹存在”“CLI list 有内容”或“测试插件装上了”。必须有原生 UI 可见集合、完整资源、受支持安装路径和直接启动的联合证据。R 的服务账号／远程功能按插件单独列示，不把它们混入文件离线安装成功率。

实现阶段运行 `npm run typecheck`、`npm test`；动 renderer-v2 再跑 `npm run check:v2`、`npm run test:v2`；打包资源另验最终 Windows/macOS 产物。所有线上／目标平台未跑项如实登记。

## 12. 当前方案的发布门禁

以下三项未解决前，可以评审本方案、推进原型，不能发布“全部官方插件打开即见”的功能承诺：

1. **全量可见性**：参考集合 U 在 API Key 模式的原生 V 是否能够完整展示，尤其仅云端／需官方身份的条目。
2. **完整资源交付**：三个远程来源以及未来新增来源是否有稳定本地安装方法，是否经得起原生自同步。
3. **分发依据与目标平台验证**：每个资源的可分发依据、真实 Windows 用户身份和原生 UI，以及 Mac arm64/x64、Finder/Dock、默认/自定义 root、首次初始化和更新逐项通过。

门禁失败时保留精确缺项与证据，不把功能改成“精选插件已就绪”、不要求客户补开加速、不伪装授权。此 PR 交付可执行的完整方案；实际实现、发布和账号能力验证在后续工作中完成。
