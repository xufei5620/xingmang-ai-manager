## 逐项证据、修复方案与验收

### #2：普通星芒账号误用同组其他不限额 Key——已修复

**当前证据：**`electron/new-api-client.ts:2639` 在候选复用前检查托管命名边界，`4085–4108` 区分聊天与工具的命名、匹配条件并保护已有额度限制。`electron/new-api-client.test.ts:3506–3574` 覆盖聊天/工具分离、长分组名回退、较新的手工 Key 或带模型/IP 限制 Key 不被误选。不能只看“同分组”就选择最新 Key。

**复用证据：**`本地证据/issue-2-key-reuse.output.txt`：同组存在受限托管 Key 与较新无关不限额 Key 时，仍选择原托管 Key。相关当前源码与已审快照相同。

**处理与验收：**无需再次修复；保留不同用途、不同托管名称、同组新旧 Key 混排的回归。确保改名或回收逻辑后，较新的无关不限额 Key 仍不能取代既有受限 Key。此结论不覆盖 #3 的跨分组迁移，也不覆盖 F01 的陈旧编辑表单。

### #3：历史账号换订阅分组丢失额度和到期日——仍存在

**触发与影响：**历史账号原工具 Key 已限额或设置到期日，订阅变化使工具转到另一个分组。新分组未找到可复用 Key 时，创建的是默认不限额、永不过期 Key；旧 Key 已用完的情形也没有阻止此跨组创建。影响限定于 `solov-api` 历史账号这条路径，不应泛化为所有星芒账号都如此。

**当前证据：**`electron/account-cli-provisioner.ts:436–439` 只传名称和目标分组；`electron/sub2api-relay-backend.ts:496` 只在新分组找候选，`499–503` 的用尽保护只作用于已找到的同组候选，`504–505` 创建时默认 `remainQuota: 0 / unlimitedQuota: true / expiredTime: -1`。现有 `sub2api-relay-backend.test.ts:910–928` 验证的是同组额度用完，不覆盖旧组转新组；`account-cli-provisioner.test.ts:1269–1293` 的跨组调用断言没有额度继承字段。

**复用证据：**`本地证据/03-regroup-cap-exhausted.output.txt`、`03-regroup-cap-partial.output.txt`，分别覆盖额度已用尽和仍有余额的旧 Key。

**具体修复：**迁移时按确切托管 Key 身份获取旧 Key 的最新剩余额度与到期日，后端支持时优先修改原 Key 的分组；必须新建时，将剩余额度和到期日明确传入创建接口。不能把原始总预算重新发一遍，也不能在读取旧限额失败时退成不限额。额度已用尽应明确阻止迁移后的继续使用；只有原 Key 本来明确不限额时才保留不限额。

**验收：**旧组预算 5、已用 2，迁往新组后只能剩 3、到期日不变；已用 5 时不能获得新额度；订阅结束回普通组同样保持约束；旧记录不可读、分组被删、同组混有其他不限额 Key 时均不得绕过限制。

### #8：旧登录恢复覆盖新登录凭据——仍存在

**触发与影响：**启动恢复 A 的旧凭据尚未结束，用户已经手动重新登录同一个账号。迟到的旧任务轮换凭据时仍可能写入同一持久化记录，使当前内存登录正常、重启后却使用旧凭据；若旧凭据已失效，保存的登录可能丢失。

**当前证据：**`electron/bootstrap/accounts.ts:125–131` 的凭据轮换回调检查的是候选 client 自己的 sessionRevision，再按 owner 写 vault；`electron/realm-account-vault.ts:292–298` 按账号身份替换，没有要求旧凭据版本仍匹配。`realm-account-service.ts:491` 对过时候选的拒绝发生得更晚，不能撤销已经由回调写入的旧凭据。已有同一个 client 内的迟到刷新测试，不等同于两个候选实例竞争同一 vault 记录。

**复用证据：**`本地证据/issue-8-rotation-race.output.txt`。

**具体修复：**给持久化凭据增加递增版本或不可复用的会话身份；轮换写入携带预期旧版本，在 vault 内执行比较后替换。全局账号操作代次和候选归属同时检查。仅比较 userId，或只比较旧 client 自己的 revision，不足以阻止同账号新登录被覆盖。合法的当前会话轮换仍需正常落盘。

**验收：**暂停旧恢复，完成同账号新登录，再放行旧轮换；vault 必须保留新凭据，重启仍可恢复；跨站同数字 userId、同账号 A→B→A、旧任务失败清理均不得覆盖或删除新记录。

### N3：订阅确认框停留在旧价格——仍存在

**触发与影响：**用户打开价格为 2 的套餐确认框，后台刷新后卡片价格变为 20，确认框仍保留原套餐对象。点击付款提交只有套餐 ID，无法证明订单仍按用户看到的旧价格创建。既有证据确认的是展示与提交缺少价格核对，没有进行真实扣费。

**当前证据：**`src/renderer-v2/features/account/AccountRecharge.tsx:509` 保存套餐对象快照，`998` 展示该快照价格；`electron/new-api-client.ts:3626–3636` 下单请求只携带 `plan_id`。具体文件位置以当前源码中的 `setPurchase` 与订阅下单调用为准。

**复用证据：**`本地证据/recharge-price-evidence.json` 及同组离线夹具。

**具体修复：**确认状态保存套餐 ID 和报价版本，列表更新、价格变化、停售或支付方式失效时作废原确认。下单前获取新报价并要求用户重新确认变化。要彻底关闭“确认后、提交前”竞争，服务端也须接受期望价格/报价 ID/版本并原子校验；只刷新前端不能宣称消除了最后一段竞争。

**验收：**确认框打开后 2→20，原确认按钮不能按旧信息继续提交；二次确认后才允许；停售、支付方式变更、跨账号迟到报价均不得沿用旧确认。

### N6：密码已改成功，记住的仍是旧密码——仍存在

**触发与影响：**服务端已处理改密，但最终响应因断网丢失。程序将其当成失败，保存的旧密码没有作废，下次自动填入的就是错误密码。

**当前证据：**`electron/new-api-client.ts:3948–3988` 先验证安全凭证、再 PUT 新密码，后一步响应丢失会抛错；`electron/ipc/handlers/account.ts:259–262` 只有成功返回后才更新记住的密码。

**复用证据：**`本地证据/password-committed-response-lost.output.txt`，模拟服务端提交成功但客户端未收到结果。

**具体修复：**区分明确未提交的拒绝与提交结果不明的传输错误。后者将对应账号的记住密码标为待确认或清除，提示用户用新密码重新确认；不能把未经确认的新密码直接当作成功，也不能自动重复改密。若后端提供安全的结果核对接口，可以先核对再更新。所有清理必须绑定发起时账号。

**验收：**mock PUT 已提交后断开响应，下次登录不再静默自动使用旧密码；原密码错误等明确拒绝仍保留适当状态；处理中切账号不得清掉另一个账号的记住密码。

### N9：检测中途打开客户端后，遗漏自动补切线路——仍存在

**触发与影响：**外部客户端最初未运行，在线路检测/模型列表等待期间被打开。此时程序正确推迟写配置，但没有保存自动重查标记；以后关闭客户端，自动补切仍不会执行。

**当前证据：**`electron/external-client-route-service.ts:480` 的重试要求 `routePending && routeRecheck`；`869–871` 的迟到运行中分支只补 `routePending: true`，没有 `routeRecheck`。本文件从旧快照到当前的变更没有修改这两段逻辑。

**复用证据：**`本地证据/external-route-pending-results.json` 与 `external-route-pending-repro.cjs`。

**具体修复：**将“客户端运行中而推迟”统一构造为可重试状态，在支持自动线路的账号/模式下同时保存待切线与重查条件；沿定时与前台唤醒入口重试。保留历史账号手动模式原有语义，任务与目标账号及线路绑定。

**验收：**最初关闭→检测中打开→本次不写→后来关闭→定时或唤醒补写；最初就运行中的既有正常路径不回归；切账号后不得补写旧账号计划。该项跨外部客户端模块，只保留旧 N9 一次计数。

### D11：七日花费跨账号缓存——仍存在

**触发与影响：**前端先取得 A 的账号范围，切换账号后再查询花费，后一个查询可能已经属于 B；写缓存时却仍采用 A 的范围。这份错误缓存可跨重启持续存在。

**当前证据：**`src/renderer-v2/features/tools/week-spend.ts:116` 取得范围，`131` 再查询，`135–137` 用先前范围落缓存；`157–158` 的外层作废检查不能撤回已经发生的持久化。`electron/realm-account-service.ts:581–602` 能保证单次调用归属，不能自动把两个独立 IPC 调用变成同一账号事务。

**复用证据：**`本地证据/accounts-renderer-extra-repro.output.json`：切回 A 后出现 B 的历史花费缓存；旧复现记录中序列为 `[900,900,900,900,900,900,100]`，而 A 的预期均为 100。

**具体修复：**让查询接收预期账号 scope 并在主进程校验，或把范围与数据合成同一次归属明确的返回；返回数据携带 scope。前端在每次缓存写入前核对账号代次，不只在最终 setState 前核对。切换账号和退出时同步作废未完成写入。

**验收：**暂停 A 的范围查询，切到 B 后继续；A 的内存和持久缓存都不能出现 B 的数据；重启读取仍正确；A→B→A 和旧失败晚返回也须按代次判旧。

### D21：自动切线重试成功，遗漏重开工具提醒——仍存在

**触发与影响：**故障自动切线首次读配置或写入失败，后续重试成功。配置虽已更新，但正在运行的 Codex/Grok 仍可能用旧配置；界面漏掉重开工具提醒，用户会以为已全部恢复。

**当前证据：**`electron/tool-route-follow-service.ts:203–205` 安排重试时只传 `reason: retry` 和 providers，没有保留 `fault`；`297–303` 成功后仅在 `request.fault === true` 时检查运行状态并生成重启提醒。

**复用证据：**`本地证据/network-route-retry-repro.json`：故障重试成功写入 1 次，却检查运行状态 0 次、hint 为 null；立即成功的对照检查 1 次并提示 Codex 正在运行。

**具体修复：**为每个待处理 provider 保存故障来源、账号代次与目标线路，重试时继承，成功完成并处理提醒后再清除。不能仅靠一次函数调用的临时布尔值；并发合并时也不能让手动请求冲掉另一工具的故障上下文。账号变更或服务销毁后清理旧上下文。

**验收：**故障首次读/写失败，重试成功且 Codex/Grok 仍运行时必须出现正确提醒；已关闭时不提示；普通手动切换不额外提示；多 provider 合并、重试上限、dispose 和切账号均不串状态。

### D25：登录超时后留下未回收服务器会话——仍存在

**触发与影响：**登录的总超时包含等待旧账号工作结束的时间。真正登录请求发得较晚，服务器已创建会话，但外层先报超时并销毁候选；迟到的成功响应被拒绝，随后没有退出该会话。影响是多出未管理的登录会话，未验证生产的设备数限制或实际会话数量。

**当前证据：**`electron/realm-account-service.ts:155–163` 使用 Promise.race；`274–275` 在 quiesce 前计算 deadline；`326` 使用剩余预算；`337–342` 对尚未形成 authenticated 状态的候选只 dispose。`electron/new-api-client.ts:3314–3320` 在解析登录响应及 cookies 前先拒绝过时尝试，失去了后续清理该会话的正常路径。

**复用证据：**`本地证据/accounts-candidates.output.json` 的 `loginDeadline`：界面结果 TIMEOUT，mock 服务端会话 1 个、logout 请求 0 个，本地未登录且未保存账号。时间被缩放为总预算 200ms、排空 120ms，未访问真实后端。

**具体修复：**分别定义排空和登录的预算，传播可取消信号，同时为未提升为当前账号的迟到成功保留受控退出路径。Abort 只能终止本地等待，不能证明服务器未创建会话；不得在清理旧候选时撤销已经提升的新会话。

**验收：**排空耗时 27 秒、登录响应 5 秒的边界应有明确一致的策略；外层超时后迟到成功须被回收一次且不能写 vault；尚未发起请求就超时不发登录/退出；明确登录失败不伪造会话；新的当前会话不被旧清理取消。

### D26：不同账号站点的花费提醒互相压住——仍存在

**触发与影响：**星芒账号与历史账号恰好都有数字 userId 7。异常花费提醒的基线和静默记录只用 `7`，因此某站点先提醒后，另一个站点的有效提醒可能被压住。

**当前证据：**`electron/balance-alerts.ts:125–130` 将 `String(userId)` 作为账号键，即使已取得的 scope 包含 realm；读基线与记提醒都沿用该数字键。

**复用证据：**同一 `accounts-candidates.output.json` 的 `spendCollision`：两个站点各发生 6 美元花费，预期提醒 2 次，实际 1 次，保存键只有 `7`。

**具体修复：**改用稳定的 realm/站点 origin/userId 复合身份作为持久键；不要使用每次登录都变的 revision，否则重登会重置静默。迁移旧纯数字记录时不能让一条旧记录同时压住两个站点。

**验收：**两站相同数字 userId 各应独立提醒；同站同用户的原有静默窗口跨重启仍有效；重登不重复提醒；不同站点切换不共享基线。

### F01：改名把刚设好的额度上限取消——仍存在

**触发与影响：**先在工具额度区把 Key 设为限额，再到仍持有旧数据的密钥管理列表改名。编辑表单仍携带“不限额”的旧值，完整提交把刚设好的限制覆盖掉。界面另一处可能仍显示 5 美元，造成额度状态不一致。

**当前证据：**`src/renderer-v2/features/account/ToolKeyLimits.tsx:144–150` 写后只刷新自己；`src/renderer-v2/pages-account.tsx:911–919` 从旧列表生成编辑值，`943–948` 提交完整字段；`electron/new-api-client.ts:3910` 虽读取最新记录，`3924–3928` 的到期日、限额开关和剩余额度仍采用客户端旧输入，所以这次 GET 没有防住额度覆盖。

**复用证据：**`本地证据/accounts-key-stale-result.json` 与 `accounts-key-stale-control.json`：限额后改名将 unlimited 从 false 改回 true；先刷新密钥列表的对照保持 false；网络为离线 mock，没有真实扣费。

**具体修复：**Key 写入后让各视图共享失效通知；打开编辑时重新取最新详情。同时把“只改名”等编辑意图传给主进程，未编辑的额度/到期日由最新记录保留。确实修改金额字段时使用期望版本/旧值冲突检查，不以陈旧全量表单覆盖。仅增加某一处 reload 无法覆盖用户先打开弹框、再从别处改额度的竞争。

**验收：**设限额 5 后不刷新列表直接改名，限额与到期日保持；先打开编辑再修改限额，也不能被旧弹框覆盖；主动取消额度限制仍正常；分组与到期日变化同样不被无关编辑覆盖；切账号后旧编辑不得作用于新账号。

## 已复核的保护与剩余限制

- `account-work-gate` 会在切换开始后拒绝新的账号操作，等待真正的旧 handler 完成，并在返回时校验代次；不是只丢弃外层 Promise。`realm-account-service.ts:581–602` 对旧成功和旧错误都做归属校验，因此不能仅见异步 `await` 就推断跨账号操作成立。
- 本轮全文复读 `payment-status-reader.ts`：创建时捕获 user/site/realm/revision，查询前后均检查，归属失效后保持失效；同账号暂时网络失败可重试。相应窗口测试不会把第三方页面上的“付款成功”文字当作独立到账证明。
- 参考 `本地证据/accounts-summary.md`：上一轮 56 个离线时序场景通过，包括 Key 创建/撤销/兑换 36 项、服务查询 14 项、浏览器查询 6 项。这里仅引用已有保护的证据，不把它们计作本轮执行，也不以其替代上面列出的缺失组合用例。
- 本专项没有核验后端当前线上版本、真实计费、真实订阅价格或支付商状态。服务器 413 专项由 root 单独整合，不属于这 102 个文件的离线源码结论。
