# 服务状态文件（service-status.json）与坏版本回退

更新目录上放一份小文件，发布者不用发版就能让已装好的客户端：说一句「服务正在维护」、
撤回一个坏版本（还没升的人不再升，已经升上去的人可以退回）、让新版本先只推给一部分电脑、
要求低于某个版本的人先更新再用（强制更新）、告诉客户端站上改了名的分组现在叫什么（分组对照）、
告诉客户端各工具现在默认用哪个型号、哪些型号已经下架（型号表）。
客户端的读法在 `electron/service-status.ts`，界面在 `src/renderer-v2/features/app/MaintenanceNotice.tsx`。

只有 **0.2.10 及以后**的客户端认这份文件，更早的版本不受影响。三件事都可以在 GitHub 上点按钮完成，不用手改文件。

## 它在哪

和更新清单 `latest.yml` 放在同一个目录：

```
https://updatesnew.shenfengwl.fun/xingmang-manager/service-status.json
```

（R2 桶里的路径是 `xingmang-manager/service-status.json`。）测试包如果打包时换了更新地址，
它读的是那个地址下的同名文件，可以拿来演练。

0.2.18 起，Windows 正式版在星芒账号走直连时，更新清单和这份文件都改从服务端的直连地址读
（`https://xm-direct.solov.cc/xingmang-manager/service-status.json`，见 `electron/update-feed-route.ts`）。
那边给的应该是同一份内容，我们只改上面那份；改完两边都打开看一眼，对不上就请服务端查那边有没有缓存（推测：没核实过那边会不会缓存）。

## 客户端怎么用它

- 启动时在后台读一次，之后每 15 分钟读一次；正在维护时改成每 5 分钟一次，好让维护一结束提示就消失。
- 读不到（没这个文件、没联网、超时、内容不是 JSON）一律当作**没在维护**，不报错、不挡启动。
- 撤回名单和分批放量不跟着这一次走：哪次没读到，就接着用最近一次读成功的那份，免得网差的电脑一次没读到
  就当成「什么都没撤回、全部放开」（#1055）。这份记在电脑上（数据目录里的 `release-guard.json`），重新打开
  软件后先用记下的，读到新的再换。最低版本不记：撤掉强制更新以后，读不到文件的电脑不能还一直被拦着。
  从来没读成功过的电脑仍按没撤回、不限量算（定了不做「从没读到就不推」，免得网差的客户一直收不到新版）。
  只有 0.2.20 及以后的客户端会记。
- 撤回名单和分批放量只让新的盖旧的（0.2.20 起，#1157 第 10 条）：文件里的 `updatedAt` 比电脑上记着的那份早，
  就当这是某条线路、某个 CDN 节点给的旧副本，撤回名单和放量不跟着它退回去（维护提示、最低版本照旧跟着这一次走）。
  所以**手改文件时要么把 `updatedAt` 改成现在的时间，要么整行删掉**；别把一份旧文件原样传回去还留着旧时间，
  读到过新文件的电脑会不认它。`updatedAt` 比电脑上的时钟晚一天以上的当没写。
- 打开维护时，右上角出一条「服务正在维护」：先是你写的那句话，后面固定跟一句「这不是你这边的问题，
  不用重新登录，也不用改任何设置，维护结束后会自动恢复」。没写那句话时用默认说法。
- 没登录也看得到：欢迎页右上角有，登录框里也有一份（登录框会盖住角落）。
- 用户可以关掉角落那条；你改了说法（比如把预计恢复时间从 22:00 改成 23:00）它会再出现。
- 写了结束时间的话，过了这个时间客户端自己当维护结束，防止维护完忘了关。

## 怎么打开、关闭（推荐：在 GitHub 上点）

1. 打开仓库的 **Actions** 页，左边选 **service-status**，右边点 **Run workflow**。
2. 「维护提示」选 **on: 打开** 或 **off: 关闭**。
3. 打开时可以填：
   - 「给用户看的一句话」：例如「服务升级中，预计今晚 23:00 前恢复。」最多 200 字，只写一句普通的话，不要放链接。
   - 「结束时间」：北京时间，写成 `2026-09-24 23:00`。可以留空。
4. 点绿色的 **Run workflow**。
5. 等它停在 **Waiting**，点进去，先往下看 **preview summary** 那一块：写的是批了以后线上的状态文件会是什么样，
   有「批之前看一眼」或黄色提示的先看清（见下面「强制更新」里「批的时候会多打提示的两种情况」）。没问题再点
   **Review deployments** → 勾 **release** → **Approve and deploy**。
   （和正式发版用的是同一个环境、同一组 R2 凭据，所以每次都要你点这一下。preview 那一段在批准之前先跑，
   不用凭据、不写线上；填错了它就红，不会走到等批准那一步。）
6. 跑绿就生效了，日志最后一步会写「客户端下一次读取就会看到这一份」。

留空的项不会动线上已有的内容：比如只想关维护，选 off 其余都不填就行。

如果它红在「线上的状态文件读回来不是有效的 JSON 对象」：多半是缓存或网站临时回了一张网页。它故意停下，
因为照空白重建会把撤回名单和分批放量一起抹掉。过几分钟重跑；还不行就用浏览器打开上面那个地址看看，
内容真坏了就按下面「备用」一节在 Cloudflare 后台传一份好的。回滚（rollback-release）读同一个文件，也会同样停下，这时线上什么都还没改。

**核对**：浏览器打开上面那个地址，看到的就是客户端读到的内容。

这个按钮要 release 环境里已有这四个 secret：`R2_ACCOUNT_ID`、`R2_BUCKET`、`R2_ACCESS_KEY_ID`、
`R2_SECRET_ACCESS_KEY`（正式发版用的就是它们）。缺哪个，第一步就会红并写出缺的名字。

## 备用：直接在 Cloudflare 后台改

GitHub 用不了的时候：

1. 在电脑上新建一个文本文件，命名为 `service-status.json`，内容照下面「文件长什么样」写，存成 UTF-8。
2. Cloudflare 后台 → **R2** → 你的桶 → 进 `xingmang-manager` 文件夹 → **Upload**，选这个文件，覆盖同名文件。
3. 浏览器打开上面的地址核对。如果看到的还是旧内容，多半是缓存，等几分钟再看。

关维护的办法是把 `"active": true` 改成 `false` 再传一次。别删掉这个文件：安装教程页每次更新下载按钮前都要读它，读不到就停止更新（见下面「坏版本回退」最后一条）。

## 坏版本回退

发出去的版本有严重问题时，**一键回退**：

1. Actions → **rollback-release** → **Run workflow**，「退回到哪个版本」填上一个好版本。下面拿「线上是坏的 `0.2.11`，退回 `0.2.10`」举例。
2. 点 Run workflow，停在 Waiting 时 **Review deployments** → 勾 **release** → **Approve and deploy**。
3. 它会依次做：
   - 先核对：`0.2.10` 的备份清单在不在、确实比线上旧，再把它要的每个安装包从更新目录完整下载一遍，大小、指纹、blockmap 都要和清单记的一字不差。哪条不对就停下，线上什么都不改。
   - Windows 那份清单还要过更新包签名（见 `docs/RELEASING.md`「更新包签名」）：备份本来带签名的验签；加签名之前发的老版本，要和 GitHub Release 上同版本的安装包逐字节对上才补签，对不上就停下。GitHub Release 上找不到那个安装包时照样退回，但认签名的新客户端会停在被撤回的版本上（日志里有一条黄色提示）。
   - 在状态文件里把线上那个版本（`0.2.11`）加进撤回名单。从这一刻起，还没升上去的人不会再被推送 `0.2.11`。
   - 把更新清单换回 `0.2.10` 的备份，再完整复核一遍更新目录。
4. 已经装了 `0.2.11` 的人，下次检查更新（启动时、每 3 小时、或自己点）会看到「建议退回稳定版本」「发布者撤回了 0.2.11。建议装回 0.2.10」。
   之后和平时的更新一样跟着「自动更新」开关走（0.2.12 起默认开着）：开着的在后台下好，退出时或下次打开时自动装回去
   （Windows 会弹授权窗口）；关着的要自己点下载、再点「重启安装」。（按 `electron/updater.ts`、`electron/auto-update-install.ts`
   看是这样，往回装这一路没在真机上演过。）
5. 让安装教程页也停发 `0.2.11`：打开 https://github.com/xufei5620/codex-tutorial-cn/actions/workflows/sites.yml → **Run workflow** → 分支选 `main` → **Run workflow**。
   一两分钟后两站的下载按钮退到上一个没被撤回的版本（不点的话等下一次定时运行，最长约 12 小时）。

要知道的几件事：

- 备份是正式发布时自动存的（`manifests/<版本>/latest.yml`、`latest-mac.yml`，Linux 对外发过以后还有 `latest-linux.yml`、`latest-linux-arm64.yml`）：每次发新版，都会先把线上那一份按它的版本号存起来，
  新版本自己也存一份。所以只能退回到**这个功能上线（0.2.10 发布）之后还在线上待过**的版本。
- 客户端最低只肯退到 **0.2.9**（`electron/updater.ts` 的 `rollbackFloorVersion`）：万一更新目录被人拿到，也没法借退回把大家装回更老、有已知问题的版本。以后某一版修了安全问题，把这个下限抬到那一版。
  这个下限只在客户端里：rollback-release 本身不查它，填一个比下限还旧的版本照样会跑完（见下面 `0.2.10` 那一段）。
- 能不能退，看下面「现在能退到哪」。
- 退回只对 **0.2.10 及以后**的客户端有效。更早的客户端不认撤回名单，会一直停在当前版本，直到出了更高的修好的版本。
- 能修的话，优先发一个更高的修好版（比如 `0.2.12`）：撤回名单里的人会直接被推到它，不用退回。退回是修好版来不及时的止血办法。
- 退回装的是旧程序，新版本改过的本机数据格式旧版本可能不认识。发版说明里写了「数据迁移」的版本，退回前先在自己电脑上试一次。
- 各平台分开看：比如只有 Windows 升到了坏的 `0.2.11`、Mac 线上还是 `0.2.10`，退回 `0.2.10` 时 Mac 那一半直接跳过（日志写「线上已经是 0.2.10，这个平台不用退回」），只退 Windows。某个平台线上比要退回的版本还旧，照样第一步就停。
- Linux：线上没有 Linux 清单（开关没打开过，见 `docs/RELEASING.md`「Linux 开关」）时直接跳过。对外发过以后 x64 和 arm64 两份清单一起退，版本号和 Windows / Mac 共用，撤回名单也共用。Linux 最早只能退到它**第一次对外发的那一版**：再早的版本没有 Linux 的包和备份，那次回滚会对 Linux 报一条黄色提示、Linux 保持不动，别的平台照样退。
- 退回之后，**别再重跑那个坏版本的 publish-release**：发布前会读一次状态文件，版本在撤回名单里就停下，线上什么都不改。修好了请提升版本号再发；真要让它原样重新上线，先在 service-status 的「撤回的版本」填 `-0.2.11` 把它移出名单。
- 修好版发出去后，`0.2.11` 留在撤回名单里就好，不用删：停在它上面的人不受分批放量限制，会最先拿到修好版。
- 安装教程页（第 5 步）只看撤回名单，不看维护和分批放量。它退回的上一版来自腾讯云 COS 下载清单的 `history`（最近 3 个旧版本，见 `docs/COS-SYNC.md`）；被撤回、或低于「最低版本」的旧版不会给，一个都不能给时那个平台不提供，三个平台都不能给时页面显示「安装包正在准备，暂时无法下载。」。教程站读不到这份状态文件时那次更新会失败、网站保持原样，所以别删这个文件。
- **service-status、rollback-release 和正式发布的上传那一步会排队，一次只跑一个。** 它们都是先读线上、再写回去，
  同时跑的话后写的会盖掉先写的。所以某一条停在 Waiting 或 Pending 时，先看是不是另一条正在跑或正等你批准：
  等它跑完（或把它 Reject 掉）再批这一条。注意 GitHub 同一组里只留一个排队的：已经有一条在排队时再点一条，
  先排的那条会被取消（什么都没写），要的话重新点一次。正式发布只有最后上传那一段排队，前面出包不受影响。

也可以只撤回、不换清单：在 **service-status** 里「撤回的版本」填坏的那个版本号（比如 `0.2.11`）。这样没升的人不会再升，已升的人等修好版。安装教程页同样点一次上面第 5 步的 `sites`；以后把版本移出撤回名单（填 `-0.2.11`）时也点一次，下载按钮就恢复。
但撤回名单只有 0.2.10 及以后的客户端认：还停在 0.2.8 或更早的人照样会被推送坏版本，要挡住他们只能把更新清单换掉（也就是跑 rollback-release）。

### 现在能退到哪

截至 **2026-10-08**：正式发过的是 `0.2.10`、`0.2.12`、`0.2.13`、`0.2.14`、`0.2.15`（GitHub 上各有 tag 和 Release），线上是 `0.2.15`。
`0.2.9`、`0.2.11`、`0.2.16`、`0.2.17` 都没有正式发过（只出过测试包，或者攒进了下一版），更新目录里没有它们的清单，也就没有备份。
每次正式发布都会把发布前线上那一份和新版本自己那一份存进 `manifests/<版本>/`，所以上面每个正式版本都应该有备份
（推测：沙箱读不到更新目录，没逐个打开核对；填错了也不要紧，rollback-release 第一步发现没有备份就停下，线上什么都不改）。

| 线上是坏的 | 「退回到哪个版本」填 | 要知道的 |
|---|---|---|
| `0.2.15`（现在） | `0.2.14` | |
| `0.2.18`（下一版） | `0.2.15` | 0.2.15 的 Windows 备份清单没有更新包签名，工作流会拿 GitHub Release 上的 0.2.15 安装包逐字节对上后补签（那个安装包在，2026-10-08 查过），0.2.18 的 Windows 客户端才肯装回去 |
| 以后的版本 | 上一个正式发过的版本 | 不能低于客户端下限 `0.2.9` |

填一个比下限还旧的版本（比如 `0.2.8`）也会跑完，但效果只是**撤下**坏版本：更新清单换回旧版、坏版本进撤回名单，挡住还没升上去的人
（包括不认撤回名单的 0.2.8、0.2.9）；已经装了坏版本的人不会被退回去，他们会看到「这个版本有已知问题」「修好的版本准备好后，这里会提示你更新」，
停在原地等修好版。`0.2.10` 刚发出时只能这么做，因为当时它的上一版 `0.2.9` 没有正式发过。

## 分批放量

新版本先只给一部分电脑，没问题再全放：

1. **发布之前**，在 **service-status** 里「分批放量」填 `0.2.11 20`（版本号、空格、百分比），跑完。
2. 再照常发布 `0.2.11`。自动检查更新时只有大约两成电脑会看到它；用户自己点「检查更新」的不受限制。
3. 观察一段时间没问题，再跑一次 service-status，「分批放量」填 `0.2.11 100` 或 `none`，全部放开。观察时想看新版本铺开了多少，跑一次 update-feed-stats（见下面「看各版本有多少人在用」）。

一定要先设放量再发布：反过来的话，发布到设置之间检查更新的人都会拿到新版本。哪台电脑在「两成」里是固定的，
不会每次检查换一批人。

放到一半发现问题、想先停住：「分批放量」填 `0.2.11 0`。之后自动检查一个都不推，用户自己点「检查更新」的照样拿得到，已经装上的不受影响。
修好了填回 `0.2.11 20` 接着放；问题严重就改用上面的撤回或回退。

想先只给少数人试、观察后再全放（手动灰度）：发布前填 `0.2.11 0`，发布后自动检查谁都不推，只有自己点「检查更新」的人拿得到；
观察没问题再填 `none`。这段时间里撤回名单上的版本、低于「最低版本」的电脑、不读这份文件的 0.2.8 和 0.2.9 照样会拿到新版本，
从安装教程页下载的新客户在 `cos-sync` 跑完后也是新版本。

## 强制更新（最低版本）

某个旧版本有严重问题、必须让大家先升上来时用。**只有 0.2.11 及以后的客户端认这一项**：
0.2.8、0.2.9 根本不读这份文件，0.2.10 读但不认这一项，它们照旧只在首页挂一条能关掉的「新版本可以安装」。

**打开**：

1. 先确认要求的那个版本已经正式发布了（比如要大家至少到 `0.2.13`，就先把 `0.2.13` 发出去）。
2. Actions → **service-status** → **Run workflow**，「最低版本」填 `0.2.13`，其余留空。
3. 点 Run workflow，停在 Waiting 时 **Review deployments** → 勾 **release** → **Approve and deploy**。
4. 跑绿就生效。版本低于 `0.2.13` 的客户下一次读这份文件（打开软件时，或开着的最迟 15 分钟）就会看到。

**客户看到什么**：整个界面上盖一层提示，关不掉（没有叉，按 Esc 也不行）：

- 标题「这个版本需要更新后才能继续用」
- 正文「为了让工具和账号正常工作，请先更新到 0.2.13 或更新的版本。点「立即更新」，新版本会自己下载并装好，中间会重启一次，账号和设置都会保留。」Windows 上多一句「装的时候如果弹出「是否允许更改」，点「是」。」
- 一行「现在是 0.2.12，将更新到 0.2.13」
- 按钮只有「立即更新」和「联系客服」。点「立即更新」后按钮依次变成「正在检查新版本…」「正在下载 42%」「正在重启安装…」，装好自动重开。
- 哪一步失败了，标题、原因和按钮与更新页、首页气泡同一套：「检查更新失败 / 下载更新失败 / 安装更新失败」+ 原因，按钮变成「重试 / 重新下载 / 重新安装」，并多出一个「打开下载页」（打开安装教程页的下载那一段，`electron/app-download-page.ts`，客户自己下安装包装；那一页跟着撤回名单走，见上面「坏版本回退」第 5 步）。

**不会把客户困住的几道保护**：

- 最低版本不能填得比线上正在发的版本还高：工作流会先读线上各平台的更新清单（Linux 两个架构各一份，没发过的平台跳过），高了就红，报「最低版本 … 比线上正在发的 … 还高」，线上什么都不改。
- 万一还是出现了找不到新版本的情况（比如新版本被撤回），客户端检查后发现没有可装的新版本，就不拦，客户照常用。
- 这份文件读不到、「最低版本」写错（比如写成 `0.2`、`latest`、`0.2.13-beta`），都当作没有最低版本。
- 低于最低版本的电脑不受分批放量限制，检查时一定能拿到新版本。

**批的时候会多打提示的两种情况**（#1114，只提示、不拦）：0.2.19 发出去 12 分钟，一次运行就清掉了「先给两成」、
又把最低版本抬到 0.2.19，所有低于它的电脑当天都被强制更新，批的人点批准时看不出这一层。现在 preview 那一段遇到下面
两种情况会在运行页面上打黄色提示，「批之前看一眼」里也有同样的话：

- 这次设的最低版本，包出来还不满 24 小时（按线上更新清单里的出包时间 `releaseDate` 算；出了包隔很久才发布的，
  算出来会比实际在客户手里的时间长）。
- 同一次运行既把线上还没全放开的分批放量清成 `none`，又改了最低版本。

服务端已经先改了、照 `docs/RELEASING.md`「服务端已经先改了、旧版本不能用了」那几步做、在测试电脑上演过的，
看到这两条照常批；不是的话 **Reject**，先放量观察，过一天再设最低版本。最低版本原样重填一遍、或者填 `none`，都不提示。

**取消**：同样跑一次 service-status，「最低版本」填 `none`。客户端下一次读到就不拦了。

**在测试电脑上演一遍**（不影响客户）：要一个带这段代码、但版本号比线上低的测试包。比如线上已经发了 `0.2.11`，
从版本号还是 `0.2.10` 的分支出一个测试包装到测试电脑上，「最低版本」填 `0.2.11`。真实的 0.2.10 客户不认这一项，
0.2.11 客户不低于它，只有这台测试电脑会被拦住。演完填 `none` 取消。

## 只管某几种安装包（0.2.20 起）

哪天只有一种安装包坏了（比如只有 Intel 版的 Mac 包），撤回、分批放量、最低版本都可以只管那一种，
不用连 Windows 和 M 系列芯片版一起撤回（#1155 第 5 条）。在 **service-status** 里照常填，版本号后面接 `@` 和平台：

| 想做什么 | 填在哪 | 填什么 |
|---|---|---|
| 只撤回 Intel 版 Mac 的 `0.2.20` | 「撤回的版本」 | `0.2.20@mac-x64` |
| `0.2.21` 先不自动推给 Intel 版 Mac，别的照常全放 | 「分批放量」 | `0.2.21 0@mac-x64` |
| 只要求 Intel 版 Mac 至少到 `0.2.21` | 「最低版本」 | `0.2.21@mac-x64` |

平台的写法：

| 写法 | 指的是 |
|---|---|
| `windows` | Windows（各种架构） |
| `mac` | Mac 两种包都算 |
| `mac-x64` | Mac Intel 版 |
| `mac-arm64` | Mac M 系列芯片版 |
| `linux` | Linux 两种包都算 |
| `linux-x64`、`linux-arm64` | Linux 对应架构的包 |
| `windows-x64` | Windows x64 包（Windows 目前只出这一种，和 `windows` 管的是同一批电脑） |

几种一起写用 `|` 隔开，比如 `0.2.20@mac-x64|linux-arm64`。写错了（比如写成 `mac-intel`）运行直接红，线上什么都不改。
`windows-arm64` 也会红：Windows 只出 x64 安装包，ARM 电脑上模拟跑着的也是它，客户端把自己算成 `windows-x64`，
写 `windows-arm64` 一台也撤不到（#1335 第 7 条）。以后真出了 ARM64 包再放开。

客户端怎么对：Windows、Linux 看自己跑的是哪个架构的包；Mac 上 Intel 机就是 `mac-x64`，M 芯片机是 `mac-arm64`，
M 芯片机上经 Rosetta 跑着 Intel 版的两种都算（装着的是 Intel 包，更新时会换成 M 系列芯片版），多算只会多拦。

要知道的几件事：

- **只有 0.2.20 及以后的客户端分得清平台。** 0.2.19 及以前的照旧对所有平台生效：撤回照旧整版撤回、分批照旧所有平台一起分批，
  只会拦得更多，不会漏掉；最低版本照旧对所有平台都拦。所以带平台的最低版本仍然不能高于**任何一个平台**正在发的版本，
  工作流照旧拿所有平台的更新清单比，高了就红。
- **管到的客户端全不认平台时，带 `@` 运行会红**（#1335 第 9 条）。撤回看的是跑着那一版的客户端：`0.2.18@mac-x64`
  撤的是所有平台的 0.2.18，所以 0.2.20 以前的版本不能带 `@`。分批放量和最低版本管的是比它低的客户端：
  `0.2.20 20@mac-x64`、`0.2.19@mac-x64` 管到的全是 0.2.19 及以前的，所以不比 0.2.20 新的也不能带 `@`。去掉 `@` 再填就行。
- **撤回名单只加不减照旧。** 同一个版本再写别的平台就合起来（先 `0.2.20@mac-x64`、再 `0.2.20@linux` = 两种都撤）；
  不带 `@` 再写一次就改回对所有平台撤回。已经对所有平台撤回的版本不能直接改成只撤一种（那等于替别的平台移出名单），
  运行会红；真要这么改，同一次填 `-0.2.20 0.2.20@mac-x64`，先移出再加。移出照旧写 `-0.2.20`，不带平台。
- 分批放量只有一条：重新填一次就整条替换，不带 `@` 就是对所有平台分批。最低版本同理，不带 `@` 重设就改回对所有平台都拦，`none` 一起去掉。
- 只撤了某一种安装包的版本，publish-release 照样当它在撤回名单里，不让再发同一个版本号：修好了照旧提升版本号再发。
- rollback-release 不分平台：它撤回的版本对所有平台都撤。
- 安装教程页（第 5 步的 `sites`）推测只看撤回名单里的版本号，带平台的也当整版撤回，Windows 和 M 系列芯片版的下载按钮也会退到上一版
  （那个仓库的代码没核过）。

## 换线路时怎么改工具配置

0.2.18 起，星芒账号的「自动」连接线路换了以后，客户端只把四个工具配置里的那一个地址改到新线路，文件其余内容原样（定点改写）。万一定点改写出了问题，不用发版就能切回以前的做法：重新同步 Key、整份重写工具配置。

1. Actions → **service-status** → **Run workflow**，「换线路时怎么改工具配置」选 `merge: 整份重写（老办法）`，其余留空。
2. 在 release 环境点 **Approve**。

客户端下一次读到状态文件（最迟 15 分钟）起，再换线路就走老办法。切回来选 `targeted: 只改地址（默认）`。
历史账号一直是老办法，不受这一项影响；0.2.17 及更早的客户端不认这一项。和别的几项一样，只有开着自动更新的安装包才读状态文件，开发构建、关了更新的一直是定点改写。

## 分组对照（xm 站改分组本名时用）

new-api 的分组没有编号：Key、可用分组接口、倍率配置全按名字认。星芒在客户端里写死了 Claude Code、Codex、Grok
和画图各用哪个分组（`electron/catalog.ts` 的 `managedCliKeyProfiles`、`electron/ai-chat-protocol.ts` 的
`IMAGE_SKILL_GROUP_NAMES`），站上改一次本名，这些名字就对不上了。xm 站上同一家有好几个分组（Claude 四个、GPT 和
Grok 各两个），靠名字里的词也认不出改了名的是哪个。0.2.19 起客户端先看这里的分组对照，对不上再照旧认。

对照只管星芒账号（xm 站），历史账号不看。只改分组的「说明」不用动它。

**怎么写**：Actions → **service-status** → **Run workflow**，「分组对照」填

```
claude=Claude 新名字|Claude-MAX订阅; codex=GPT 新名字|GPT-中转/订阅; grok=Grok 新名字|Grok-中转/订阅; image=画图新名字|图片模型-中转/订阅
```

- 能写的用途只有 `claude`、`codex`、`grok`、`image`（画图）。Codex 那一项同时决定 AI 对话没选过分组时默认用哪个；
  `image` 那一项列的每个名字，AI 对话和画布在那个分组里都只列图片模型（和写死的 `图片模型`、`图片模型-中转/订阅` 一样）。
- 每项按先后列名字，用 `|` 隔开；客户端在这个账号此刻能用的分组里挑**排在最前**的那个。改名过渡期把新名字写在前、
  老名字写在后：服务端还没加上新名字时客户端用老的，加上了就换新的。
- 几项之间用分号隔开；只写要改的那几项，没写到的照线上保留。`codex=none` 去掉一项，整个填 `none` 清空。
- 名字要和站上一字不差（大小写、空格、全角半角都算）。`|`、`｜`、`;`、`；` 都当分隔符，名字里不能有这几个字。
  跑完看日志里「分组对照：」那一行，核对每样用途拆出来的名字对不对。
- 写进对照的名字，客户端只在服务端允许这个账号用的分组里找；写了一个账号用不了的名字，等于没写这一个。

**什么时候写**：在服务端删掉老名字**之前**。客户端启动时读一次对照、之后每 15 分钟再读；哪次没读到就接着用上一次
读到的。本机有工具还没存 Key 时（新装、换电脑、换账号，或者账号一直签不出某个工具的 Key）签 Key 按对照来，
连带已经存着的那几把也会按对照换到新分组；画图技能每次同步、AI 对话每次列分组也都按对照来。三个工具的 Key 都存在
本机的电脑开机不问分组（离线也要能用），不会因为对照变了就重签，靠的是服务端把老 Key 记的分组一起改过去。

**对照管不到的**（要服务端兜着，步骤见服务端那份改名清单）：

- 0.2.18 及更早的客户端不认对照，只认写死的老名字：老名字删掉后，它们新登录、换电脑签不出 Key。
- 服务端已经发出去的 Key 记的是老名字：不跟着改过去，删老名字那一刻这些 Key 就用不了。
- 画布（无限画布）的默认图片、视频分组不看对照，按名字认（`canvas-v2/src/library/media-groups.ts`）：老名字
  `图片模型-中转/订阅`、`视频模型-中转/订阅` 在时用老名字；0.2.19 起老名字删了再认 `图片模型`、`视频模型`，
  还认不出就看名字里带「图片」「视频」的分组，只有恰好一个时才认，视频认不出就留空让客户自己选。0.2.18 及更早
  只认带「中转」的名字，图片会退到列表第一个分组、视频会退到带 Grok 的分组。

## 型号表（型号换代、站上下架型号时用）

Claude Code、Codex、Grok 各用哪个默认型号写在客户端里（`electron/cli-model-defaults.ts`）。站上下架一个型号、
或者换一个新的默认型号，以前要发版才能跟上（比如 gpt-5.5 下架，客户在 0.2.19 之前一直报错）。0.2.20 起这里写一张型号表，
客户端和自带的那份合并，不用发版。

每个工具可以写三样，都可以不写：

- `default`（默认）：新配的工具用哪个型号。登录自动配置、配置窗口给没设型号的工具预选、「换用别家模型」里标「Codex 默认」的
  都是它（#1154）。账号模型列表里没有它时，先退回上一代，再退回程序自带的默认。
- `previous`（上一代）：以前的默认型号，按先后排。账号还没上新默认时先用它；配置里还是它、账号已经能用新默认的，
  打开工具前问一次「要不要换成新型号」，客户点了才换。改了默认以后，程序自带的那个默认自动算上一代，不用再写。
- `retired`（已下架）：两个站都已经下架的型号。配置里还是它、账号也确实不再列它的，下次打开星芒时直接换成默认型号，
  不问（留着它每一轮都报错）。和程序自带的下架名单合在一起算，这里不能把自带名单里的型号救回来。
  默认、上一代都不在账号列表里时，Claude Code、Grok 只换成同系列里最新的（下架的 claude-opus-5 换 claude-opus-4-8）；
  同系列也没有就这次不换，打开工具前问客户，那一问 Claude 按 Opus > Sonnet > Haiku 劝（#1154）。Codex 照旧换成第一个能对话的型号。

**几道保护**：

- 只碰星芒用当前账号写的配置。客户改过 Key 或地址的、手填 Key 的、官方账号的一律不动。
- 只改型号那一处，文件里别的设置、注释一个字不动（#1154）。跟着换的只有本来就跟着型号走的：Codex 的 `review_model`
  和旧型号一样才换，Claude Code 的「Default」那一行指着旧型号才换。客户用 /model 自己选的型号要是也下架了，同样换成同系列的。
- 默认型号只在这个账号模型列表里真有的型号里挑：写一个账号用不了的名字等于没写这一个，写错也写不进配置。
- 下架名单只换掉账号已经不再列出的型号：账号还在列的，写进名单也不换。
- 换之前先备份（「设置 › 备份迁移」里能找回）；工具正开着或看不出开没开的，这次不换，过一阵再试。
- Codex 的 WebSocket 开关跟着型号走：换到 GPT 型号是开，换到别家型号是关，客户自己改过的不动。

**怎么写**：Actions → **service-status** → **Run workflow**，「型号表」填

```
codex.default=gpt-7; codex.previous=gpt-6-astra; codex.retired=gpt-5.5|gpt-6-luna
```

- 能写的工具只有 `claude`、`codex`、`grok`，每个工具三样：`default`、`previous`、`retired`。中间用点连起来。
- 几个型号名字用 `|` 隔开；几样之间用分号隔开。`default` 只能写一个。
- 只写要改的那几样，写到的那一样整样换掉（比如 `codex.retired=gpt-5.5|gpt-6-luna` 是把下架名单换成这两个），
  没写到的照线上保留。`codex.retired=none` 去掉一样，`codex=none` 去掉一个工具，整个填 `none` 清空。
- 名字要和模型列表里一字不差，只能用字母、数字和 `. _ - : / @ +`。默认型号又写进下架名单、同一个型号既是上一代
  又是下架的，工作流直接报错，线上什么都不改。跑完看日志里「型号表：」那一行核对。

**什么时候写**：站上下架型号的同时（或之后）写 `retired`；新默认型号站上**已经开好**以后再写 `default`。客户端启动时读一次、
之后每 15 分钟再读；哪次没读到就接着用上一次读到的。读到的型号表还记在电脑上（数据目录里的 `cli-model-hints.json`），
打开星芒那次没读到也按上次记下的算，从来没读成功过才用程序自带的；读成功、里面没写型号表的那次也记下来，撤掉型号表以后
读不到文件的电脑不会一直按撤掉前那份走（#1154）。下架型号的替换在打开星芒时做，开着的星芒
要等下次打开（或开机那轮没换成、过一阵再补的那次）。

**型号表管不到的**：

- 0.2.19 及更早的客户端不认，照旧用自带的那份。
- AI 对话的默认型号（`gpt-5.6-sol`）不归这张表管。分组里不再列它时，新对话挑同系列里最新的（#1154）。
- 这张表改的是客户端怎么挑型号，站上开不开这个型号要服务端定。

## 看各版本有多少人在用

Actions → **update-feed-stats** → **Run workflow**，「统计最近几天」默认 7，点 Run workflow。不用批准，一两分钟跑完。
点进那条运行，结果在 Summary 页上：各版本占全部电脑的比例（Windows、Mac、Linux 分开列）、这次统计的口径、
下过最新两版安装包的电脑后来怎样、还停在旧版本的电脑下过新版没有，最后附一张按请求算的对照表。

**怎么数的**：0.2.10 起的客户端打开时、开着时每 15 分钟读一次这份 service-status.json，请求里带着自己的版本号
（Electron 默认的 User-Agent，里面有「星芒AI管理工具/0.2.15」）。工作流拿只读令牌查 Cloudflare 的访问统计，把这些请求
按版本、系统和来源 IP 归拢，每台电脑只算它这段时间里最后一次读时的版本。来源 IP 只在运行时拿来去重，不写进日志和结果。

**只有比例，没有台数**：仓库是公开的，运行页谁都能看，写台数等于告诉别人有多少客户。

**口径：各平台数到的是哪些电脑**（Summary 页每次都会写一遍）：

- Mac、Linux：各个版本都读这里的状态文件（直连那份更新目录只给 Windows，见 `electron/update-feed-route.ts`），数字可信。
- Windows：0.2.18 以前的正式版都读这里。**0.2.18 起走洛杉矶线路的，更新和状态文件都改从 `xm-direct.solov.cc` 读**，
  只在服务端日志里；走 CF 线路的照常数得到。所以 Windows 一栏 0.2.18 及以后偏低，它们升级前读的那一次还算在旧版本上，
  旧版本偏高。偏多少这里算不出来，要服务端按同样的办法（状态文件请求 User-Agent 里的版本号，按来源 IP 去重）数 xm-direct 的日志。
  这是 2026-10 把 Windows 挪到洛杉矶线路时没算进去的代价：Cloudflare 这边从此数不到升上去的 Windows。
- 这段时间一次都没开过星芒的电脑不在里面。

**下过新版安装包的电脑后来怎样**：自动更新也从这个目录下安装包（Windows 的 `Setup.exe`、Mac 的 zip）。按来源 IP 和系统，
把每台电脑第一次下某一版的小时，和它之后读状态文件时的版本对上，分成三种，每种写占同一系统里下过的电脑的比例。
这段时间里被下过的最新两版各一张表：最新那版刚发出去时大多还没轮到检查，只看它看不出装没装得上。

- 之后以这一版或更高的版本读过：装上了（下了 0.2.20、后来直接到 0.2.21 的，在 0.2.20 那张表里也算装上）。
- 之后（晚于下载那个小时）还以旧版读：还没装上。分不出装失败和下好了没重启，0.2.18 以前的版本要客户自己点「重启安装」。
- 之后再没出现：Mac 就是之后没再开星芒；Windows 也可能是装好后改走洛杉矶了，这里分不开。拿 Mac 这一格当「关了没再开」的
  大概比例，Windows 多出来的那部分大致是装好后改走洛杉矶的（推测）。
- 0.2.18 起的 Windows 走洛杉矶时连安装包也从 xm-direct 下，它们升下一版时这一项也看不到。

**还停在旧版本的电脑下过新版没有**：只看这段时间里最后一次读状态文件时还低于最新那版的电脑，按它停在的版本和系统，
写两个比例：这段时间里从这里请求过比它自己新的安装包（下没下完都算）的；一次都没请求过，但新版出来以后读过更新清单
（Windows 的 `latest.yml`、Mac 的 `latest-mac.yml`，electron-updater 每次查更新都先读它）的。更新清单的请求 UA 是
electron-builder、不带版本，只按来源 IP 和清单的文件名对上电脑。几种情况办法不一样，**抬最低版本（强制更新）之前先看这一节**。
没机会下的不算进表里：一台电脑没下过，而它最后一次出现时比它新的版本还没人下过，或者第一次有人下到还不满 6 小时
（开着的星芒 3 小时查一次更新，两轮加上下载的时间），就当它没轮到，不算「没下过」，表下面另写一句这种占几成。
不扣掉的话，统计好几天时，新版出来前就不再出现的电脑会全算成「没下过」。「出来」按这段时间里第一次有人下到算，
所以统计开头 6 小时里最后出现的电脑也会被扣掉（那时新版其实早就有了），扣多不扣少。

- 下过还停着：下得到，只是没装（或没下完）。自动更新要等退出星芒或下次打开才装，点关闭缩到托盘不算退出；强制更新时点「立即更新」会当场装。
- 没下、查过更新：查到了新版却没去下，多半是关了「自动更新」（关了只提示、不下），也可能是查完以后出了错（推测）。
- 没下、也没见查过：新版出来以后，星芒开着的时候还没轮到查（推测 Mac 合盖睡着的时间不算进 3 小时），或者查的那次没被记下。
- Mac 的安装包、更新清单和状态文件在同一个地址，读得到状态文件就连得上，Mac「没下过」不是一开始就连不上（下到一半断了的算「下过」）。
  Windows 走洛杉矶的从 xm-direct 查和下，这里看不到，Windows 几列偏低；Mac 几列只看这里就够。
- 强制更新只拦打开了窗口的人（拦住时点「立即更新」会当场下载并装上），窗口一直缩着的照旧停着，见 #1380。
- Cloudflare 抽样记的时候（10-24 那次最多每 10 次记 1 次），一台只请求一两次安装包的多半漏记，看到的「下过」只是下限。
  这时每格多一个括号里的估算：看到的每台按那个小时的抽样倍数算成几台（一台请求了好几次时会估高）。实际在两个数之间。
  更新清单的请求被抽样时，「没下、查过更新」也只是下限，Summary 页上会写明。

**看不到、不准的地方**：

- 0.2.8、0.2.9 不读这份文件。
- 同一个网络出口下的几台电脑算一台（IPv6 按同一个 /64 网段算，因为电脑的 IPv6 临时地址隔一阵就换），换过网络的电脑会算成几台。
  「下过新版安装包后来怎样」也靠这个把下载和之后的读对上，换了网络的电脑会落进「没再出现」。
- Cloudflare 只留最近一段时间的统计，填的天数比它留的多时只统计它留着的那段，Summary 页上会写明。
- 请求多的时候 Cloudflare 会抽样记录（2026-10-09 第一次跑，7 天里最多每 3 次记 1 次），Summary 页上会写明；占比很小的几行只能粗看。

**令牌**：仓库 Secrets 里的 `CLOUDFLARE_ANALYTICS_TOKEN`（Settings → Secrets and variables → Actions → Repository secrets，
不在 release 环境里）。shenfengwl.fun 在放更新桶 `xingmang-updates-new` 的那个 Cloudflare 账号里，**不在 solov.cc 那个账号**，
令牌要在那边建。运行报「令牌被 Cloudflare 拒绝」就是过期或被删了，重建：右上角头像 → 我的个人资料 → API 令牌 →
创建令牌 → 最下面「创建自定义令牌」，权限两行「区域｜区域｜读取」和「区域｜Analytics｜读取」，区域资源选
「包括｜特定区域｜shenfengwl.fun」，摘要里只有这一个域名、两项读取才对。建好把那串粘进这个 secret。别从现成模板改，
模板会多带一堆权限；也别去改已有的令牌。只有 Analytics 一行时令牌看不到域名，运行会报「令牌看不到 shenfengwl.fun」。
「特定区域」的下拉框里找不到 shenfengwl.fun，说明登的不是放更新桶的那个账号，改权限没用，要换到那个账号再建。

## 文件长什么样

```json
{
  "maintenance": {
    "active": true,
    "message": "服务升级中，预计今晚 23:00 前恢复。",
    "until": "2026-09-24T15:00:00.000Z"
  },
  "badVersions": ["0.2.10"],
  "rollout": { "version": "0.2.11", "percent": 20 },
  "minimumVersion": "0.2.11",
  "toolRouteRewrite": "merge",
  "accountGroups": {
    "codex": ["GPT 新名字", "GPT-中转/订阅"],
    "image": ["画图新名字", "图片模型-中转/订阅"]
  },
  "cliModels": {
    "codex": { "default": "gpt-7", "previous": ["gpt-6-astra"], "retired": ["gpt-5.5"] },
    "claude": { "previous": ["claude-opus-5"] }
  }
}
```

- `maintenance.active`：只有写成 `true`（不带引号）才算在维护。
- `message`：可省略。控制字符会被去掉，超过 200 字的部分客户端不显示。
- `until`：可省略。必须带时区（上例是 UTC，等于北京时间 24 日 23:00）。
- `badVersions`：撤回的版本，写成 `["0.2.10"]`。只认 `0.2.10` 这种写法。
- `badVersionPlatforms`：撤回名单里哪几个版本只撤哪几种安装包，写成 `{ "0.2.20": ["mac-x64"] }`（平台写法见「只管某几种安装包」）。
  版本号必须同时写在 `badVersions` 里，不然不算；有一个平台写错，客户端就当这个版本对所有平台撤回。0.2.20 起的客户端认。
  客户端读的时候会去掉空白、转成小写，版本号去掉前导 `v`（`"v0.2.20": ["Mac-X64"]` 也算只撤 Intel 版 Mac），
  service-status 工作流读线上这份时照同一套规整，预览和下一次运行都跟客户端说的一样（#1335 第 8 条）。
- `rollout`：分批放量，写成 `{ "version": "0.2.11", "percent": 20 }`。只管某几种安装包时加 `"platforms": ["mac-x64"]`，
  写错了当对所有平台分批。
- `minimumVersion`：最低版本，写成 `"0.2.11"`，只认三段数字。手改文件时同样不要填得比线上正在发的版本高。
- `minimumVersionPlatforms`：最低版本只拦哪几种安装包，写成 `["mac-x64"]`；写错了当对所有平台都拦。
- `toolRouteRewrite`：只认 `"merge"`（换线路时整份重写工具配置）；不写、写别的都是只改地址。
- `accountGroups`：分组对照，键只认 `claude`、`codex`、`grok`、`image`，值是按先后排的名字数组，每项最多 8 个；
  空的、超过 128 字、带控制字符的名字客户端跳过。
- `cliModels`：型号表，键只认 `claude`、`codex`、`grok`，每个是 `{ "default": "…", "previous": […], "retired": […] }`，
  三样都可以不写；`previous` 最多 8 个、`retired` 最多 32 个。名字不是字母数字开头、带空白引号括号、超过 128 字的
  客户端跳过那一个。
- `updatedAt`：改动时间，GitHub 按钮会自动写。0.2.20 起客户端拿它比撤回名单和放量哪份更新（见上面「客户端怎么用它」）；
  手改时改成现在的时间或删掉。
- 其他字段客户端不认，留着也没关系。
