# 直连线路适配需求·补充：中转上线与 3 个必修问题（本期只做 xm）

> 2026-10-08，服务端整理。基于 10-07 线上 0.2.17 的实测数据，是服务端此前交给客户端的《直连线路适配需求》的补充。
> 本仓库公开，文中用户以「用户 A–D」代称；具体账号、IP 等由服务端私下提供。

## 1. 服务端变化：xm-direct 后面接入洛杉矶 CN2 GIA 中转（客户端不用改地址）

- `xm-direct.solov.cc` 的 DNS 之后会改指向一台洛杉矶中转机。这台机器走 CN2 GIA 精品线路，按 SNI 把 TLS 流量原样转发到原来的直连入口，**不解密、不改证书**。本期只做 xm，`api-direct.solov.cc` 不变。
- **客户端什么都不用改**：域名、证书、白名单都不变。
  - **不要**把中转机的 IP 写进代码、配置或测试固件；以后换机器时，服务端只改 DNS（TTL 60 秒）。
  - **不需要**新增「中转线路」选项，「直连」线路背后就是中转。
- 测试方法：在本机 hosts 里把 `xm-direct.solov.cc` 指向服务端提供的测试 IP，直连流量就会经过中转。测试 IP 找服务端要，不要提交进仓库。

## 2. 必修问题一：Codex 等 CLI 的配置没有跟随当前线路（最重要）

**现象**（10-07 线上，0.2.17，以服务端 nginx 日志和 new-api 日志逐条对照为准）：

| 用户 | 管理工具自己的请求 | Codex 实际用的地址 |
|---|---|---|
| 用户 A | 注册、登录、建 key、读余额**全部走直连** | `xm.solov.cc`（CF） |
| 用户 B | 走直连，生图（主进程）也走直连 | `xm.solov.cc`（CF），当天 24 次以上 |
| 用户 C | 在直连和 CF 之间来回切 | `xm.solov.cc`（CF），20 次以上 |
| 用户 D | 走直连 | `xm-direct.solov.cc`（正常） |

- 用户 A 全程都在直连上，Codex 配置却写成了 CF 地址。说明**写 CLI 配置时选地址的逻辑，和管理工具自己选线路的逻辑不是同一套**，而不只是写配置那一刻碰巧切到了 CF。
- Codex 对话占流量的绝大部分。这个问题不修，中转就几乎用不上。

**要求**：
1. 写 Codex、Claude Code、Gemini、Grok 的配置时，`base_url` 用**当前生效线路**的域名（直连时就是 `https://xm-direct.solov.cc/v1`）。
2. 线路切换后，自动按新线路改写 CLI 配置，沿用 `config-files.ts` 的备份和合并逻辑，并提示用户重启正在运行的 CLI。
3. 诊断页显示：当前线路、CLI 配置里实际写的地址，两者不一致时给出提示。
4. 排查一下用户 D 能走直连、A/B/C 不能，代码路径上有什么区别（新注册还是老账号登录、首次配置还是升级迁移、线路是自动还是手动等）。

## 3. 必修问题二：线路好坏判断不能把「慢」当成「坏」

**现象**：用户 C（联通，直连下行约 50KB/s）在直连和 CF 之间来回切。每次切走的时间点，都正好是 `/api/notice` 下载慢的时候（当时公告 2MB：9.5s、11.5s、60s，内容只下了一半就被客户端放弃，nginx 记录的 `resp_bytes` 只有 19 万到 70 万字节）；某一时刻还一次性取消了 7 个直连请求（nginx 记为 499）。

**要求**：
1. 判断线路是否故障，只看两类信号：
   - 健康检查：xm 用 `GET /api/status`；
   - 网络层失败：DNS 解析失败、TCP 连不上或超时、TLS 握手失败或被重置、连接被重置。
2. 业务请求（尤其是大响应）慢或超时，只在本请求内重试或降级，**不触发切换线路**。
3. **防抖**：
   - 健康检查连续失败 N 次（建议 3 次）才切到 CF；
   - 回切直连前，直连要连续健康 M 分钟（建议 5–10 分钟）；
   - 两次切换之间至少间隔若干分钟。
4. 日志带上线路 id，切换时记录原因。

## 4. 必修问题三：公告要缓存

- 现在大约每分钟拉一次 `/api/notice`。服务端已经把公告从 2.7MB 压到约 400KB，但仍然不该每分钟全量下载。
- **要求**：
  - 按内容哈希或至少每 10 分钟拉一次，内容没变不重新渲染；
  - 首屏不要被公告下载卡住；
  - 公告下载失败或超时不影响线路判断（见第 3 节）。

## 5. 暂缓：接入 sub2api 的直连（api-direct）

**本期只做 new-api（xm），sub2api 暂不做。** 原需求里 api-direct 的部分先不要动：sub2api 账号相关请求和写进 CLI 的地址继续用 `api.solov.cc`。中转目前也只转发 `xm-direct.solov.cc`，等服务端通知后再做 api-direct。

## 6. 以后可能要做（先知悉）

部分网络会按域名掐断 `*.solov.cc`。服务端以后可能给直连再加一个非 solov 的备用域名，指向同一台中转。客户端要能配置「同一线路的多个候选域名」，按健康检查选可用的那个，并且所有候选都要被识别为星芒中转。

## 7. 验收补充

- [ ] hosts 把 `xm-direct.solov.cc` 指向测试中转 IP 后：管理工具登录、余额、key、公告、更新检查都正常；Codex 的 `base_url` 是 `xm-direct.solov.cc`，对话正常。
- [ ] 新注册、老用户登录、从老版本升级三种情况下，Codex 配置都跟随当前线路。
- [ ] 人为限速，比如把直连下行限到 30KB/s：线路**不来回切**，公告慢慢下完或用缓存，Codex 正常。
- [ ] 人为断开直连（比如 hosts 指到一个不可达的 IP）：约 N 次健康检查后切到 CF，CLI 配置被改写并提示重启；恢复后过 M 分钟切回。
- [ ] 诊断页能看到当前线路、CLI 配置里的地址和最近的切换原因。
