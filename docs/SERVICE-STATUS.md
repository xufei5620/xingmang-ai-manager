# 服务状态文件（service-status.json）与坏版本回退

更新目录上放一份小文件，发布者不用发版就能让已装好的客户端：说一句「服务正在维护」、
撤回一个坏版本（还没升的人不再升，已经升上去的人可以退回）、让新版本先只推给一部分电脑。
客户端的读法在 `electron/service-status.ts`，界面在 `src/renderer-v2/features/app/MaintenanceNotice.tsx`。

只有 **0.2.10 及以后**的客户端认这份文件，更早的版本不受影响。三件事都可以在 GitHub 上点按钮完成，不用手改文件。

## 它在哪

和更新清单 `latest.yml` 放在同一个目录：

```
https://updatesnew.shenfengwl.fun/xingmang-manager/service-status.json
```

（R2 桶里的路径是 `xingmang-manager/service-status.json`。）测试包如果打包时换了更新地址，
它读的是那个地址下的同名文件，可以拿来演练。

## 客户端怎么用它

- 启动时在后台读一次，之后每 15 分钟读一次；正在维护时改成每 5 分钟一次，好让维护一结束提示就消失。
- 读不到（没这个文件、没联网、超时、内容不是 JSON）一律当作**没在维护**，不报错、不挡启动。
- 打开维护时，右上角出一条「服务正在维护」：先是你写的那句话，后面固定跟一句「这不是你这边的问题，
  不用重新登录，也不用改任何设置，维护结束后会自动恢复」。没写那句话时用默认说法。
- 没登录也看得到：欢迎页右上角有，登录框里也有一份（登录框会盖住角落）。
- 用户可以关掉角落那条；你改了说法（比如把预计恢复时间从 22:00 改成 23:00）它会再出现。
- 写了结束时间的话，过了这个时间客户端自己当维护结束，防止维护完忘了关。

## 怎么打开、关闭（推荐：在 GitHub 上点）

1. 打开仓库的 **Actions** 页，左边选 **service-status**，右边点 **Run workflow**。
2. 「维护提示」选 **on: 打开** 或 **off: 关闭**。
3. 打开时可以填：
   - 「给用户看的一句话」：例如「服务升级中，预计今晚 23:00 前恢复。」最多 200 字，只写一句普通的话，不要放链接。
   - 「结束时间」：北京时间，写成 `2026-09-24 23:00`。可以留空。
4. 点绿色的 **Run workflow**。
5. 等它停在 **Waiting**，点进去 → **Review deployments** → 勾 **release** → **Approve and deploy**。
   （和正式发版用的是同一个环境、同一组 R2 凭据，所以每次都要你点这一下。）
6. 跑绿就生效了，日志最后一步会写「客户端下一次读取就会看到这一份」。

留空的项不会动线上已有的内容：比如只想关维护，选 off 其余都不填就行。

**核对**：浏览器打开上面那个地址，看到的就是客户端读到的内容。

这个按钮要 release 环境里已有这四个 secret：`R2_ACCOUNT_ID`、`R2_BUCKET`、`R2_ACCESS_KEY_ID`、
`R2_SECRET_ACCESS_KEY`（正式发版用的就是它们）。缺哪个，第一步就会红并写出缺的名字。

## 备用：直接在 Cloudflare 后台改

GitHub 用不了的时候：

1. 在电脑上新建一个文本文件，命名为 `service-status.json`，内容照下面「文件长什么样」写，存成 UTF-8。
2. Cloudflare 后台 → **R2** → 你的桶 → 进 `xingmang-manager` 文件夹 → **Upload**，选这个文件，覆盖同名文件。
3. 浏览器打开上面的地址核对。如果看到的还是旧内容，多半是缓存，等几分钟再看。

关维护最简单的办法是把 `"active": true` 改成 `false` 再传一次（或者直接删掉这个文件）。

## 坏版本回退

发出去的版本有严重问题时，**一键回退**：

1. Actions → **rollback-release** → **Run workflow**，「退回到哪个版本」填上一个好版本，比如 `0.2.9`。
2. 点 Run workflow，停在 Waiting 时 **Review deployments** → 勾 **release** → **Approve and deploy**。
3. 它会依次做：
   - 先核对：`0.2.9` 的备份清单在不在、确实比线上旧、它要的安装包都还在更新目录里。哪条不对就停下，线上什么都不改。
   - 在状态文件里把线上那个版本（比如 `0.2.10`）加进撤回名单。从这一刻起，还没升上去的人不会再被推送 `0.2.10`。
   - 把更新清单换回 `0.2.9` 的备份，再完整复核一遍更新目录。
4. 已经装了 `0.2.10` 的人，下次检查更新（启动时、每 3 小时、或自己点）会看到「这个版本有已知问题，建议退回 0.2.9」，
   下载后点「重启安装」装回去。**不会自动装**，和平时的更新一样要用户点。

要知道的几件事：

- 备份是正式发布时自动存的（`manifests/<版本>/latest.yml`、`latest-mac.yml`）：每次发新版，都会先把线上那一份按它的版本号存起来，
  新版本自己也存一份。所以 **0.2.10 发布之后，才能从 0.2.10 退回 0.2.9**；更早的版本没有备份。
- 客户端最低只肯退到 **0.2.9**（`electron/updater.ts` 的 `rollbackFloorVersion`）：万一更新目录被人拿到，也没法借退回把大家装回更老、有已知问题的版本。以后某一版修了安全问题，把这个下限抬到那一版。
- 退回只对 **0.2.10 及以后**的客户端有效。更早的客户端不认撤回名单，会一直停在当前版本，直到出了更高的修好的版本。
- 能修的话，优先发一个更高的修好版（比如 `0.2.11`）：撤回名单里的人会直接被推到它，不用退回。退回是修好版来不及时的止血办法。
- 退回装的是旧程序，新版本改过的本机数据格式旧版本可能不认识。发版说明里写了「数据迁移」的版本，退回前先在自己电脑上试一次。
- 修好版发出去后，`0.2.10` 留在撤回名单里就好，不用删：停在它上面的人不受分批放量限制，会最先拿到修好版。

- **service-status、rollback-release 和正式发布的上传那一步会排队，一次只跑一个。** 它们都是先读线上、再写回去，
  同时跑的话后写的会盖掉先写的。所以某一条停在 Waiting 或 Pending 时，先看是不是另一条正在跑或正等你批准：
  等它跑完（或把它 Reject 掉）再批这一条。注意 GitHub 同一组里只留一个排队的：已经有一条在排队时再点一条，
  先排的那条会被取消（什么都没写），要的话重新点一次。正式发布只有最后上传那一段排队，前面出包不受影响。

也可以只撤回、不换清单：在 **service-status** 里「撤回的版本」填 `0.2.10`。这样没升的人不会再升，已升的人等修好版。

## 分批放量

新版本先只给一部分电脑，没问题再全放：

1. **发布之前**，在 **service-status** 里「分批放量」填 `0.2.11 20`（版本号、空格、百分比），跑完。
2. 再照常发布 `0.2.11`。自动检查更新时只有大约两成电脑会看到它；用户自己点「检查更新」的不受限制。
3. 观察一段时间没问题，再跑一次 service-status，「分批放量」填 `0.2.11 100` 或 `none`，全部放开。

一定要先设放量再发布：反过来的话，发布到设置之间检查更新的人都会拿到新版本。哪台电脑在「两成」里是固定的，
不会每次检查换一批人。

## 文件长什么样

```json
{
  "maintenance": {
    "active": true,
    "message": "服务升级中，预计今晚 23:00 前恢复。",
    "until": "2026-09-24T15:00:00.000Z"
  },
  "badVersions": ["0.2.10"],
  "rollout": { "version": "0.2.11", "percent": 20 }
}
```

- `maintenance.active`：只有写成 `true`（不带引号）才算在维护。
- `message`：可省略。控制字符会被去掉，超过 200 字的部分客户端不显示。
- `until`：可省略。必须带时区（上例是 UTC，等于北京时间 24 日 23:00）。
- `badVersions`：撤回的版本，写成 `["0.2.10"]`。只认 `0.2.10` 这种写法。
- `rollout`：分批放量，写成 `{ "version": "0.2.11", "percent": 20 }`。
- 其他字段客户端不认，留着也没关系；GitHub 按钮会多写一个 `updatedAt` 记录改动时间。
