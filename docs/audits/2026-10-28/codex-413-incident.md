# Codex 413 与 WebSocket：结论、客户端现状与剩余缺口

> 2026-10-28 云端接手时改写本页：原稿里的服务器配置（入口套餐、各层请求体上限、后端镜像版本、内部上游名、源站日志统计）和客户那两次请求的标识、时间、客户端信息都不放进公开仓库，由项目维护者私下保留。下面只留判断结论和客户端这一侧的事实；客户端说法已对照 main `4c1e876`（#1496 合进之后）核过。

## 结论

- 客户截图里的两次 413 都是**线路1 的 Cloudflare 入口直接拒绝，没有到源站**，两次都是 **HTTP POST `/v1/responses`**，没有走 WebSocket。
- 只打一句「在吗」不等于请求小：Codex 每次会把会话历史和图片一起带上。日志没留请求体，说不出是哪张图、哪段工具输出、具体多大。
- 同一时段另有一次大请求在入口等太久变成 **524**。它是另一种失败，不能和 413 混成一个原因。
- **线路2（直连）能真实升级成 WebSocket**；**线路1 主域对 WebSocket 握手回 426**，这是有意设的：Cloudflare 上 WebSocket 一轮约 100 秒不出字就会被当闲置掐掉，Codex 要连着重连 5 次才回退（见 `electron/config-files.ts` 写 `supports_websockets` 处的注释）。去掉 426 会把这个老问题带回来。
- Codex 收到 426 后改走 HTTP，并在这个会话里一直走 HTTP（厂商行为，据 Codex 上游源码，云端没另外核），所以换线后要**完全退出 Codex 再打开**才会重新尝试 WebSocket。WebSocket 也不是无限通道：首次连接、缓存丢失或重建会话时仍可能发完整上下文。

## 客户端现在怎么处理（#1496 之后）

- `electron/codex-payload-limit.ts` 盯 Codex 会话记录，认出 `413 Payload Too Large`（只读末尾一段、不跟链接、日志不记原文和地址）。
- 星芒账号选「自动」时：先探一次线路2，通了就当场切过去，让 Codex 配置跟过去，并提示「完全退出 Codex 再打开」；线路2 也超了，提示新开对话；锁了线路1，只提示不改设置。
- 线路1 上会话记录过了 80MB 提前提醒一次。客户没看着星芒时另发系统通知。
- 不会自动重发任何请求，不会多扣钱。
- 注意：提示文字里写死了两条线路的上限数值，服务端改数值时要同步改字。

## 给客户的处置

1. 星芒账号选「自动」本来就先走线路2。客户落在线路1，说明锁了线路1，或者当时线路2 不通退回来了：先确认线路设置，让 Codex 配置的 `base_url` 落在线路2 上。
2. 保存工作后完全退出 Codex 再打开（Mac 上 Command+Q），新会话才会重新尝试 WebSocket。已有聊天保留，太大的可以用摘要加必要附件开新对话。
3. 由客户正常用一次来验收：回答或工具调用确实完成，而不是只看握手成功。这一步可能计费，审查没有代发。

## 剩余的产品缺口

| 编号 | 现状 | 还要做的 |
|---|---|---|
| H-WS-GAP-01 小探针通 ≠ Codex 大请求能发 | **#1496 补了一半**：认出 413 后自动换线或建议新开对话，有 80MB 提前提醒，不自动重放 | 524 认不出；锁了线路1、Codex 一直 413 时检查页仍显示线路正常；线路2 当时探不通的会话以后不会再帮它换 |
| H-WS-GAP-02 配置写了 WS ≠ 正在跑的会话在用 | **#1496 补了一半**：换线后专门提示重开 Codex，出提示前核对配置确实在线路2 | 看不出 Codex 实际走 WebSocket 还是 HTTP；历史账号窗口缩在托盘超过 10 分钟、界面被释放后，换线不会把界面叫醒，Codex 配置还停在线路1、也不出提示（读代码推测，没跑过） |
| H-WS-GAP-03 原生验收偏 HTTP | 没动 | 沙箱模板写的是 `supports_websockets = false`，CI 真线探测只打线路1 的小请求，实际只验到 426 回退；要补 101、426 回退、断线重连、缓存丢失、413/524 的本地模拟，真机验收要另行授权 |

## 没核实的

客户那次请求的实际大小和内容构成、当时本地的 provider 配置、是否更早试过 WebSocket、切到线路2 后真实会话能否完成，都还不知道。服务端的上限和规则不在本仓库范围内，云端没有核。
